# ChronicleDB `v0.6.0` Plan — Admission Control / Resource Protection and Storage Lifecycle

Status: **planning only**. Nothing in this document is implemented. No
production code has been changed to produce it. It does not advance any
maturity claim in [`docs/roadmap.md`](roadmap.md), and it does not
authorize starting `v0.7.0`.

Written against `main` at `481ff93` (`docs: mark v0.5.0 released`),
working tree clean, on branch `v0.6.0-planning`. Baseline capability:
`v0.5.0` (Dynamic Membership) released and closed; cluster generation
ceiling `internal/version.MaxSupportedGeneration == 2`; snapshot
`FormatVersion == 2`, `MinReadVersion == 1`.

This document is the `v0.6.0` analogue of
[`docs/dynamic-membership-plan.md`](dynamic-membership-plan.md): it is
the authoritative, implementation-ready design for the release, derived
from — and cross-checked against —
[`docs/enterprise-v1-plan.md`](enterprise-v1-plan.md) §9 (Admission
Control / Resource Protection) and §10 (Storage Lifecycle), which the
release ladder in that document's §4 bundles into `v0.6.0`.

It is detailed enough that an implementation session can execute it
end to end without inventing architecture. Where it deviates from the
literal text of `docs/enterprise-v1-plan.md` §9/§10, §26 records the
deviation, the evidence for it, and the resolution — deviations are
never silent.

## 0. Scope reaffirmation

### 0.1 In scope

1. **Admission control / resource protection** (§§3-11) — bounded
   admitted work, bounded queues, a structurally separate
   consensus/control-plane path, a separate admin lane, disk/memory
   pressure signals feeding admission, a stable rejection contract,
   and the observability for all of it.
2. **Storage lifecycle** (§§12-26) — MVCC garbage collection
   implemented as *replicated* state, snapshot-horizon enforcement,
   WAL/snapshot retention and safe deletion, disk-space accounting, a
   disk-full/low-disk state machine, fsync-failure health transitions,
   an integrity-verification scrub, and crash safety across all of it.

### 0.2 Out of scope, absolutely

Inherited unchanged from
[ADR-0001](adr/0001-v1-single-shard-static-cluster-scope.md),
[`docs/non-goals.md`](non-goals.md), and
[`docs/enterprise-v1-plan.md`](enterprise-v1-plan.md) §18:

- **No multi-shard, range, rebalancing, or distributed-transaction
  work of any kind.** Exactly one Raft group, exactly one shard, as of
  `v0.5.0` and unchanged.
- **No weakening of any `v0.5.0` guarantee.** Raft safety, `DURABILITY`,
  Snapshot Isolation, `IDEMPOTENCY`/`REQUEST OUTCOME STABILITY`,
  backup/restore, rolling upgrades, and Dynamic Membership all hold
  exactly as they do at `v0.5.0`. §27 states, invariant by invariant,
  how each is preserved.
- **No `v0.7.0` work** (Operations/Observability, Deployment, Supply
  Chain) beyond the specific metrics and endpoints §11 and §25 require
  to make *this* release's mechanisms observable.

### 0.3 The five standing constraints this plan is bound by

Restated here because every design decision below is checked against
them, and §34 audits the finished plan against them one by one:

| # | Constraint | Where honored |
|---|---|---|
| C1 | No unbounded queue disguised as admission control | §5 — every waiting goroutine occupies a slot in a fixed-capacity structure; the bound is a channel capacity, not a policy |
| C2 | No arbitrary sleep/retry-based correctness proof | §29 — every safety property is proven by a structural gate or a deterministic oracle; the two wall-clock mechanisms (queue max-wait, read-lease expiry) are liveness-only and are named as such |
| C3 | No silent data deletion under storage pressure | §19.4 — pressure tightens *admission*, never deletes data; the only deletion mechanism is GC, and GC's rule is `docs/mvcc.md` §6's, unchanged |
| C4 | No disk reclamation before the durable safety boundary is proven | §17, §22 — the `RECLAMATION BOUNDARY` invariant; the existing snapshot-durable-then-compact ordering is preserved step for step |
| C5 | Internal consensus/recovery traffic is never starved by client overload | §4 — the consensus path is a physically separate code path that no client-facing gate can reach, not a priority flag on a shared queue |

### 2.2 What is genuinely missing

1. **Every node channel is unbuffered** (`internal/node/node.go`,
   `Open`: `proposeCh`, `controlCh`, `readIndexCh`, `backupCh`,
   `precheckCh`, `membershipCh`, `membershipStatusCh` are all
   `make(chan T)`). The de facto queue is therefore *the set of
   blocked caller goroutines*, which is unbounded: one goroutine per
   in-flight HTTP request, each retaining its decoded
   `fsm.CommitTxnCommand` (up to the 1 MiB body limit) for as long as
   it waits. This is the single largest memory-exhaustion surface.
2. **No cap on `len(n.waiters)`.** A leader that accepts proposals
   faster than it commits them grows that map without bound.
3. **`http.Server` is constructed with no timeouts at all**
   (`cmd/chronicledb-node/main.go:221`: `&http.Server{Addr:…,
   Handler:…}`) — no `ReadHeaderTimeout`, `ReadTimeout`,
   `WriteTimeout`, `IdleTimeout`, or `MaxHeaderBytes`, and no bound on
   concurrent connections. (The request *body* is already bounded:
   `io.LimitReader(r.Body, 1<<20)` in `handlePropose`.)
4. **No bound on inbound peer connections.**
   `internal/transport.acceptLoop` spawns one `readLoop` goroutine per
   accepted connection with no limit and no read deadline; a dead TCP
   connection retains its goroutine indefinitely.
5. **No resource-pressure signal of any kind.** There is no
   `Statfs`-equivalent call anywhere in the tree, and no runtime
   memory sampling.
6. **No histogram primitive.** `internal/metrics` has `Counter` and
   `Gauge` only.
7. **MVCC GC does not exist.** `internal/mvcc.Store.chains` only ever
   grows (`ApplyCommit` appends; nothing removes). `mvcc.go`'s own
   package comment states this explicitly.
8. **There is no active-snapshot registry anywhere.**
   `internal/txn.Manager` does not track live `Txn`s (`Begin()` at
   `internal/txn/txn.go:182` constructs and forgets), and in
   replicated mode `internal/txn` is not in the path at all —
   `internal/sql`'s `replicatedEngine` goes `Node.BeginReadIndex` →
   `Node.Propose`, and the node retains nothing about the open
   transaction.

8a. **`mvcc.Store.Visible` is *not* the only committed-read path.**
   `internal/sql`'s `mergeScan` (`internal/sql/engine.go:307`),
   reached from **`replicatedTxn.ScanPrefix`**
   (`internal/sql/engine.go:236,241`) and from `standaloneTxn.ScanPrefix`
   (`:154`), calls `mvcc.Store.Export()` (`internal/mvcc/mvcc.go:147`
   — no `startSeq` parameter) and then re-implements the visibility
   rule locally in `visibleInChain` (`internal/sql/engine.go:344`).
   Any guard placed only on `Visible` is therefore bypassed by every
   prefix scan. §15.2 is the consequence.

8b. **`mvcc.Store` has no ordered key index.** `chains` is a
   `map[string][]Version`; the only sorted view is `Export()`, which
   materializes and sorts the *entire* key set on every call. Any
   "walk keys in sorted order" design must supply its own ordered
   access or it re-sorts the whole keyspace per call. §14.4 is the
   consequence.

8c. **`n.pendingReads` is unbounded and is scanned on the consensus
   path.** `handleReadIndex` (`internal/node/node.go:1479`) appends
   unconditionally; entries are removed only on resolution or
   leadership loss (`:1497`-`:1526`) or at shutdown (`:1318`). A
   caller that cancels its context returns from `BeginReadIndex`
   without removing its entry. `checkPendingReads` iterates the whole
   slice after **every** `processOutput` (`:1596`). §9.1 is the
   consequence.

8d. **`n.waiters` is not removed on caller cancellation.** `Propose`
   returns on `ctx.Done()` (`internal/node/node.go:1172`), but the
   waiter registered at `:1450` survives until the entry applies
   (`:1709`), the node steps down (`:1582`), or it shuts down
   (`:1313`). `len(n.waiters)` is therefore **not** bounded by any
   caller-side concurrency limit. §5.3 is the consequence.

8e. **`FSM.mu` is an exclusive `sync.Mutex`, taken by both `Apply` and
   the read-only lookups.** `FSM.Apply` (`internal/fsm/fsm.go:184`),
   `FSM.Precheck` (`:111`) and `FSM.GetOutcome` (`:133`) all take
   `f.mu.Lock()`. `GetOutcome` backs the deliberately ungated
   `/outcome` endpoint, so concurrent `/outcome` calls contend
   exclusively with the event loop's own `Apply`. §5.4a is the
   consequence.
9. **No disk-space accounting, no low-disk state, no fsync-failure
   counting, no scrub.**
10. **Snapshot retention is fixed at exactly one file**, pruned the
    moment a newer one is durable — including while that older
    snapshot may still be wanted by `processOutput`'s
    `snapMgr.Bytes(...)` call serving an `InstallSnapshot`
    (`internal/node/node.go:1547`, whose miss path logs and skips).

### 2.3 Three facts that shape the whole design

- **`internal/mvcc` is inside the determinism boundary.**
  [`docs/invariants.md`](invariants.md) `DETERMINISM BOUNDARY` names
  `internal/mvcc` explicitly, and `STATE MACHINE SAFETY`'s proof
  obligation is byte-identical state across independently constructed
  replicas. Any mutation of a version chain that is not a pure
  function of committed history breaks both. §13 is the consequence.
- **MVCC data has no on-disk store of its own.** `internal/storage` is
  used for exactly two things: WAL segment files and snapshot files.
  Version chains live in RAM and are persisted only inside a snapshot.
  "Reclaiming file space for superseded MVCC data" therefore means
  *the next snapshot is smaller*, not *a file is rewritten* (§12).
- **Long self-initiated durable operations run on the event loop.**
  `maybeSnapshot` and `handleBackup` both block ticks, heartbeats, and
  inbound Raft message reading for their whole duration; this is a
  documented, accepted `v0.1.0`-era tradeoff
  (`internal/node/snapshot_latency_test.go`'s own header says so).
  §4.4 scopes `CONTROL-PLANE NON-STARVATION` around this fact rather
  than pretending it away.

# PART A — ADMISSION CONTROL / RESOURCE PROTECTION

## 3. Admission model

### 3.1 The one-sentence model

> Work that a client can cause is admitted through a fixed-capacity
> gate on the *caller's* goroutine, before it can consume any
> event-loop time, any Raft log index, or any additional memory; work
> that consensus or an operator causes reaches the event loop through
> code paths that contain no such gate.

### 3.2 The four lanes

Lanes are **separate objects with separate capacities**, not priority
levels on one queue. There is no shared structure whose saturation one
lane can inflict on another.

| Lane | Members | Gate | Default capacity |
|---|---|---|---|
| **Lane K (consensus)** | `run()`'s `ticker.C` and `n.tr.Recv()` cases; everything they call (`tick`, `step`, `processOutput`, `applyCommitted`, `handleInstallSnapshot`, `maybeSnapshot`) | **None, structurally.** No admission type is imported by, referenced from, or reachable from these cases. | n/a |
| **Lane A1 (control plane)** | `AddLearner`, `PromoteToVoter`, `RemoveServer`, `MembershipStatus`, `UpgradePrecheck`, `FinalizeUpgrade`, `/admin/reload-tls` | `controlGate` | `-max-admin-concurrency` = 2 |
| **Lane A2 (maintenance)** | `Backup`, `Scrub` | `maintenanceGate` + a single slot per kind | `-max-maintenance-concurrency` = 2 |
| **Lane B (client)** | `Propose` (writes), `BeginReadIndex` (reads / SQL `BEGIN`) | `writeGate`, `readGate` | `-max-inflight-proposals` = 256; `-max-concurrent-reads` = 512 |

Lane A is deliberately *not* merged into Lane B even though both are
"things a caller initiates": the whole point of the split is that a
client flood must never prevent an operator from removing a dead
member, finalizing an upgrade, or taking a backup.
`-max-admin-concurrency` is small on purpose — control actions are rare
and mostly serialized upstream anyway (`SERIALIZED MEMBERSHIP CHANGE`).

### 3.2a Why Lane A is split in two

`Backup` and `Scrub` are the only caller-initiated operations in this
release whose duration is **unbounded in the input, not in the
request**: a backup export copies the whole snapshot plus the durable
WAL suffix, and a scrub reads the entire data directory at
`-scrub-bytes-per-sec` (64 MiB/s default — ~50 minutes for 200 GiB).
Membership, upgrade and TLS-reload actions are short and are exactly
the actions an operator reaches for when the cluster is sick.

If both kinds shared one gate at capacity 2, one running scrub plus
one running backup would occupy it entirely, and
`POST /admin/membership/remove` for a genuinely failed node would
return `503 admin_operation_in_progress` for the whole scrub window.
No client flood is required to produce that: the release's own new
feature would block the emergency control action Lane A exists to
protect.

**Rule CP-3.** A Lane A2 (maintenance) operation may never hold a
Lane A1 (control) slot, and the two gates share no structure. Stated
as an absence, like Lane K's: `Node.Backup` and `Node.Scrub` contain
no reference to `controlGate`, and the membership/upgrade/TLS entry
points contain no reference to `maintenanceGate`. AC-18's AST test
(§4.2) is extended to assert both directions, so the split cannot be
silently merged back by a later refactor.

Capacity 2 on `maintenanceGate`, with an additional single slot per
kind, means: at most one backup and at most one scrub at a time, and
they may overlap (backup runs on the event loop, scrub does not, so
overlapping them costs nothing a serialized pair would not also
cost). A second `/admin/backup` gets `503 admin_operation_in_progress`
exactly as §7 already specified.

### 3.3 Where the gate is *not*

Explicitly enumerated so an implementation session does not
"helpfully" add one:

- Never inside `run()`'s `select`.
- Never on `Node.step`, `processOutput`, `applyCommitted`,
  `handleInstallSnapshot`, `tick`, or any `raft.Core` method.
- Never on the follower side of replication. A follower appending
  `AppendEntries` entries is consensus work, not client work, even
  though a client ultimately caused it. Gating it would convert a
  local resource condition into a quorum-availability failure — the
  exact inversion §9 of the enterprise plan forbids.
- Never on `internal/raft`. `internal/raft` gains no import of
  `internal/admission` and no knowledge that admission exists.
- Never on `/health`, `/metrics`, `/status`, or `/outcome`. An
  overloaded node must still be able to *say* it is overloaded, and a
  client resolving an uncertain outcome by `RequestID` must not be
  shed — that is the documented recovery path from a `503`.
  **This is only sound once §5.4a lands**: `/outcome` currently takes
  `FSM.mu` *exclusively* (fact 8e), the same mutex the event loop's
  `Apply` takes, so leaving it ungated as-is would hand unbounded
  client concurrency a lock on the consensus path. §5.4a makes those
  lookups shared-mode reads, which is what turns "ungated" into
  "cheap".

## 4. Control-plane non-starvation, precisely

### 4.1 What Go's `select` already gives us, and what it does not

`run()`'s `select` chooses uniformly at random among *ready* cases, so
a permanently ready `proposeCh` does not starve `tr.Recv()` in the
scheduling sense. What it does **not** bound is:

1. the number of goroutines parked on `proposeCh <- req` (each holding
   a payload) — a memory problem, not a scheduling one;
2. the *service time* the loop spends on each admitted client request,
   which delays every other case, including heartbeats.

(1) is what the gate fixes. (2) is what §4.2-§4.4 address.

### 4.2 Structural separation, stated as an implementable rule

**Rule CP-1.** `internal/node` must contain exactly one gate
acquisition per entry point, and each must be in a method that runs on
a *caller's* goroutine (`Propose`, `BeginReadIndex`, `Backup`, `Scrub`,
the three membership methods, `UpgradePrecheck`, `FinalizeUpgrade`) —
never in a method reachable from `run()`.

**Rule CP-2.** This is enforced by a test, not by convention.
`TestAdmissionNeverReachableFromEventLoop` uses `go/parser` +
`go/ast` (both standard library, so
[`docs/dependencies.md`](dependencies.md) is untouched) to build the
static call graph rooted at `(*Node).run` over `internal/node`, and
asserts no function in that graph's transitive closure references any
identifier from `internal/admission`. Same class of structural test as
`TestControlKindRangesNeverCollide` — a property the code cannot
silently lose.

The same test additionally enforces **Rule CP-3** (§3.2a) by building
the call graphs rooted at `(*Node).Backup` and `(*Node).Scrub` and at
the six control entry points, and asserting neither closure references
the other lane's gate identifier.

### 4.3 The bound the invariant actually claims

`CONTROL-PLANE NON-STARVATION` (§27.2) claims exactly this:

> The latency of processing one inbound Raft message, and the latency
> of dispatching one heartbeat round, are not functions of client
> admission-queue depth, client request concurrency, or client
> rejection rate.

Three structures would falsify that claim if left as they are at
`481ff93`, and `v0.6.0` fixes all three rather than narrowing the
claim to fit them:

1. **`FSM.mu` exclusivity** (fact 8e). Ungated `/outcome` and
   `Precheck` take the same exclusive mutex `Apply` takes on the event
   loop, so Apply latency — and therefore inbound-message latency —
   would scale with client lookup concurrency. §5.4a converts those
   lookups to shared-mode reads.
2. **`checkPendingReads`'s unbounded scan** (fact 8c). It runs after
   every `processOutput`, over a slice with no ceiling, so per-message
   cost would scale with accumulated client reads. §9.1 adds the
   event-loop ceiling that bounds it.
3. **`ApplyAdvanceGCWatermark`'s keyspace walk** (fact 8b). An Apply
   whose cost is `O(total keys)` puts client-independent but
   unbounded work on the loop on every replica. §14.4 bounds keys
   examined per command and forbids a per-Apply full sort.

Proven by AC-6 (deterministic, `internal/node` `testCluster` tier —
see §29.3) and AC-10 (real cluster): drive the client gate to
permanent saturation and show the heartbeat/append round-trip latency
distribution is statistically indistinguishable from the unsaturated
baseline, *and* that the saturated case produces zero elections. AC-19
covers (1) specifically, by driving `/outcome` concurrently with Raft
traffic; SL-2b covers (3).

### 4.4 What the invariant deliberately does **not** claim

It does **not** claim the event loop is never blocked. Three
self-initiated operations still run to completion on it:
`maybeSnapshot`, `handleBackup`, and `handleInstallSnapshot`. `v0.6.0`
does **not** move them off the loop — doing so requires a
copy-on-snapshot of FSM state and re-proving `SNAPSHOT SAFETY`, which
is a larger change than this release's scope and would put a `v0.5.0`
guarantee at risk for a liveness gain. Instead `v0.6.0`:

1. **Bounds how often they can happen.** Backup and scrub are Lane A,
   capacity 2 and additionally serialized per kind, so a client flood
   cannot trigger either; snapshot creation stays threshold-driven and
   unchanged.
2. **Pre-empts the election timers around them.** Immediately before
   `maybeSnapshot` calls `snapMgr.Create` and before `handleBackup`
   calls `backup.Export`, the loop issues one forced heartbeat round
   (`Core.Step(InputHeartbeatTimeout)` and drains the resulting
   messages) so every follower's election timer is freshly reset at
   the *start* of the blocking window rather than at an arbitrary
   earlier point. This does not shorten the window; it makes the worst
   case one full heartbeat interval better than it is today.
3. **Measures them.** `chronicledb_event_loop_block_seconds`
   (histogram, one observation per blocking operation, one series per
   operation kind — §11.2) makes the remaining exposure a number in
   `/metrics` instead of a paragraph in a doc.
4. **Names the deferral.** §36 records "move snapshot creation and
   backup export off the event loop" as a `v0.7.0`+ item with its own
   design requirement, so it is tracked rather than forgotten.

This scoping is stated in the invariant text itself (§27.2) so nobody
can later read the invariant as a stronger claim than was proven.

## 5. Bounded queues, concurrency limits, and the limiter primitive

### 5.1 `internal/admission` — the package

New package. Imports: standard library plus `internal/metrics` only.
Imported by `internal/node`, `internal/sql`, `cmd/chronicledb-node`.
Imports nothing from `internal/raft`, `internal/fsm`, `internal/wal`,
`internal/storage`, `internal/txn`, or `internal/node` — it is a leaf
beside `internal/metrics`, which keeps
[`docs/architecture.md`](architecture.md) §5's dependency direction
acyclic.

```
type Reason string      // stable vocabulary, §8.2
type Class  int         // ClassClientWrite | ClassClientRead | ClassAdmin

type RejectedError struct {
    Reason     Reason
    RetryAfter time.Duration
    Detail     string
}
func (e *RejectedError) Error() string
func (e *RejectedError) Is(target error) bool   // matches ErrOverloaded

var ErrOverloaded = errors.New("admission: overloaded")

type Limits struct {
    MaxConcurrent int           // > 0 required
    MaxQueueDepth int           // >= 0; 0 means "no waiting at all"
    MaxWait       time.Duration // 0 means "bounded only by ctx"
}

type Gate struct { /* §5.2 */ }
func NewGate(name string, lim Limits) (*Gate, error)
func (g *Gate) Acquire(ctx context.Context) (release func(), err error)
func (g *Gate) InFlight() int
func (g *Gate) Queued() int
func (g *Gate) Stats() GateStats
func (g *Gate) SetEffectiveConcurrent(n int)   // §6.4 pressure tightening
```

### 5.2 `Gate` internals — the structural bound (C1)

```
type Gate struct {
    name  string
    slots chan struct{}   // cap == MaxConcurrent
    queue chan struct{}   // cap == MaxQueueDepth
    eff   atomic.Int64    // effective ceiling, always <= MaxConcurrent
    ...
}
```

`Acquire`:

1. **Admit to the waiting room, or reject now.**
   `select { case g.queue <- struct{}{}: default: return nil, &RejectedError{ReasonQueueFull, …} }`
   With `MaxQueueDepth == 0` the `default` always fires — pure
   immediate rejection, which is the configuration deterministic tests
   use.
2. **Acquire a slot.** `select` over `g.slots <- struct{}{}`
   (success), `ctx.Done()` (caller gave up), and — only when
   `MaxWait > 0` — a `time.Timer` (reject `ReasonQueueTimeout`). Every
   branch drains `g.queue` before returning.
3. **Effective-ceiling check.** After taking a slot, if
   `InFlight() > eff` (pressure tightened the ceiling in the
   meantime), release and reject with the pressure reason. The ceiling
   is advisory-downward only: it can never admit more than
   `MaxConcurrent`.
4. `release` is idempotent (`sync.Once`) and drains `g.slots`.

The total number of goroutines that can be inside `Acquire` at any
instant is `MaxConcurrent + MaxQueueDepth`, by channel capacity. That
is the answer to C1: the bound is a capacity, not a policy, and there
is no code path that grows it.

**Memory bound, stated numerically.** With the defaults and the
existing 1 MiB request-body limit, the worst-case resident client
request payload on a node is
`(-max-inflight-proposals + -admission-queue-depth) × 1 MiB`
= `(256 + 256) × 1 MiB` = **512 MiB**. This number must appear in
`docs/admission-control.md` as an operator-facing sizing rule, and
every default must be justified against it (§10.3).

### 5.3 The authoritative in-flight bound lives in the event loop

The gate bounds goroutines and memory. The *invariant*
(`BOUNDED ADMITTED WORK`) is about proposed-but-unapplied entries, and
that set is `n.waiters`. So `handlePropose` gains, before
`proposeAndAwait`:

```
if len(n.waiters) >= n.maxClientWaiters {
    n.metrics.AdmissionDefenseRejectionsTotal.Inc()
    req.resultCh <- proposeResult{err: &admission.RejectedError{
        Reason: admission.ReasonConcurrencyLimit, RetryAfter: time.Second}}
    return
}
```

Three properties make this the right place:

- It **cannot be bypassed**: every client proposal goes through
  `handlePropose`, on the one goroutine that owns `waiters`, with no
  lock and no race.
- It is **fail-safe** (A-12): if the caller-side gate is
  misconfigured, buggy, or bypassed, this still rejects.
- It applies to **client proposals only**. `handleControlPropose`
  (upgrade finalize), `handleMembership`, and `proposeElectionNoOp`
  never consult it — a saturated client workload must not be able to
  block a membership change or a new leader's own no-op. This is Lane
  A/Lane K priority expressed as an *absence of a check*, which is the
  only form of priority that cannot be misconfigured.

`maxClientWaiters` is set from `-max-inflight-proposals`.

**Resolved: the two mechanisms are not interchangeable, and the loop
check fires in normal operation.** An earlier draft of this section
claimed the loop check "should never fire in a correct build". That
is false, because of fact 8d: `Propose` returns on `ctx.Done()`
(`internal/node/node.go:1172`) and its `defer release()` frees the
gate slot, but the waiter registered at `:1450` survives until the
entry applies, the node steps down, or it shuts down. A canceled
caller therefore vacates a gate slot that a new caller immediately
takes, while its waiter remains.

Counterexample, which is ordinary operation and not a bug: clients
use a 100 ms request deadline against a leader whose apply latency
exceeds 100 ms. Gate in-flight cycles at 256 forever; `len(n.waiters)`
grows monotonically until the ceiling rejects. The same happens on a
leader in a minority partition, where nothing commits at all and the
gate never rejects anything.

Consequences, all binding:

- The **event-loop ceiling is the authoritative bound** on
  `BOUNDED ADMITTED WORK`. The gate bounds *goroutines and resident
  payload memory*; it does not bound `waiters`. §27.1's mechanism
  text says exactly this, and no longer says "either sufficient".
- `chronicledb_admission_defense_rejections_total` is a **normal
  operating signal under client cancellation**, not a bug signal. It
  is documented in `docs/admission-control.md` as "clients are
  abandoning requests faster than they apply", with the tuning
  response (raise `-max-inflight-proposals`, or lengthen client
  deadlines).
- AC-14 asserts the counter stays zero only in the admission tests
  that contain **no** client cancellation, and the new **AC-20**
  asserts it *does* fire, and that `len(n.waiters)` never exceeds the
  ceiling, under a deliberately cancel-heavy workload. Release gate 5
  is scoped to match.

### 5.4 Entry-point mapping

| Entry point | Gate | Acquired | Released |
|---|---|---|---|
| `Node.Propose` | `writeGate` | first statement, before `Precheck` (§5.7) | `defer`, covering every return including `ctx.Done()` and `ErrNodeStopped` |
| `Node.BeginReadIndex` | `readGate` | first statement | `defer`. **Note:** released when `BeginReadIndex` returns, *not* when the transaction ends — transaction lifetime is bounded by the read lease (§15.3), a different mechanism with a different purpose |
| `Node.Backup` | `maintenanceGate` + backup single-slot | first statement | `defer` |
| `Node.Scrub` | `maintenanceGate` + scrub single-slot | first statement | `defer` |
| `Node.AddLearner` / `PromoteToVoter` / `RemoveServer` | `controlGate` | inside `membershipRequest` | `defer` |
| `Node.UpgradePrecheck` / `FinalizeUpgrade` | `controlGate` | exported wrapper only; the unexported `upgradePrecheck` called *from* `FinalizeUpgrade` does not re-acquire (it would self-deadlock at capacity 1) | `defer` |
| `Node.MembershipStatus`, `Node.Status`, `Node.Metrics`, `FSM.GetOutcome` | none | — | read-only and cheap **only after §5.4a**; must stay available under overload |
| `sql.Session` statement execution | `sqlGate` (§9.2) | per statement | `defer` |

No entry point acquires both `controlGate` and `maintenanceGate`
(Rule CP-3, §3.2a).

### 5.4a Resolved: `FSM.mu` becomes an `RWMutex`

Fact 8e: `FSM.Apply`, `FSM.Precheck` and `FSM.GetOutcome` all take
`f.mu.Lock()` — one exclusive `sync.Mutex`. `GetOutcome` backs
`/outcome`, which §3.3 declares permanently ungated because it is the
documented recovery path from a `503`. Left as-is, that combination
hands unbounded client concurrency an exclusive lock on the mutex the
event loop needs, which is the precise hazard §5.7 cites as its own
reason for moving the gate ahead of `Precheck` — open on the one path
the plan promises never to shed.

**Decision: `FSM.mu` becomes a `sync.RWMutex`. `Apply` and every
mutating control-command apply keep `Lock()`; `Precheck`,
`GetOutcome`, and `lookupLocked`'s read-only callers take `RLock()`.**

- This is a pure concurrency change inside `internal/fsm` with no
  effect on `Apply`'s serialization (the event loop is still the only
  writer), no effect on determinism, and no format implication.
- Go's `RWMutex` blocks new readers once a writer is waiting, so a
  stream of `/outcome` calls cannot starve the event loop's `Apply`.
- It is what makes §5.4's "read-only, cheap" claim and §3.3's
  ungated-endpoint decision true rather than aspirational, and it is
  what lets §4.3's invariant be stated without an exception clause.
- Proof: **AC-19** drives `-max-http-connections` worth of concurrent
  `/outcome` and `/status` calls against a leader under sustained
  Raft traffic and asserts `chronicledb_raft_message_process_seconds`
  p99 stays within the unsaturated baseline; its negative control
  reverts to the exclusive mutex behind a test hook and asserts the
  oracle detects the regression.

This does **not** reverse §5.7's decision — see §5.7's restated
rationale.

### 5.5 Rejection is immediate and fast

With `MaxQueueDepth = 0`, rejection is one non-blocking channel send
that fails — no allocation, no lock, no syscall. With a queue
configured, the *maximum* time before a caller learns it was rejected
is `min(MaxWait, ctx deadline)`. Neither value participates in any
correctness argument (C2): every safety property in §27 holds for
`MaxWait = 0` and for `MaxWait = ∞` alike. They exist only to convert
"unbounded latency" into "bounded latency plus an explicit `503`",
which is A-3's entire content.

### 5.6 Fail-safe direction (A-12)

Three independent expressions of "a broken limiter rejects":

1. `NewGate` returns an error for `MaxConcurrent <= 0`, and
   `cmd/chronicledb-node` treats that error as fatal at startup. There
   is no "limits disabled" configuration and no flag value meaning
   unlimited: `-max-inflight-proposals=0` is a startup error, not "no
   limit".
2. The event-loop check (§5.3) rejects independently of the gate.
3. `Acquire` has no path returning a nil error without a held slot —
   enforced by a `-race` test running `MaxConcurrent+1` concurrent
   acquires against a gate whose releases are withheld, asserting
   exactly one rejection and exactly `MaxConcurrent` successes, at
   1000 iterations.

### 5.7 Resolved: the gate runs *before* `Precheck`

`Node.Propose` currently calls `n.fsmachine.Load().Precheck(cmd)`
before touching the event loop, resolving a known `RequestID` without a
Raft round.

**Decision: acquire the write gate first, then `Precheck`.**

**Restated rationale (§5.4a changes the lock, not the decision).** An
earlier draft justified this solely by "`Precheck` takes `FSM.mu`,
which the event loop also takes." Once §5.4a makes `Precheck` a
shared-mode read, that argument no longer carries the decision on its
own. Two independent reasons do, and they are the binding ones:

1. `Precheck` calls `fingerprintOf(cmd)`
   (`internal/fsm/fsm.go:19`), which hashes the command's full
   mutation set on **every** call. That is unbounded client-caused
   CPU work, and admitting before doing any per-request work is this
   release's general rule, not a lock-specific workaround.
2. Even with an `RWMutex`, an unbounded reader population still
   forces the event loop's writer to wait for the current reader
   cohort to drain on every `Apply`. Bounding the reader population
   on the *proposal* path costs nothing and is free of the
   `/outcome` path's "must never be shed" constraint.

Consequence, documented in the error contract: under overload, a retry
of an already-decided `RequestID` can be rejected with `503` rather
than returning its recorded outcome. This is safe (`503` is retryable
and records nothing), and the cheap read-only `GET /outcome` path —
deliberately ungated (§3.3) — remains the correct way to resolve a
known `RequestID` under load. Rejected alternative: exempt duplicates
from the gate. Rejected because "is this a duplicate?" cannot be
answered without doing the very work the gate exists to bound.

## 6. Resource-pressure signals

### 6.1 Sampling, never probing in the hot path

A single `admission.PressureMonitor` goroutine samples every
`-resource-poll-interval` (default `5s`) and stores an immutable
`Pressure` snapshot in an `atomic.Pointer`. Gates read the pointer;
nothing on a request path or the event loop ever makes a syscall or
calls `runtime/metrics`.

```
type Pressure struct {
    DiskFreeBytes  uint64
    DiskTotalBytes uint64
    HeapBytes      uint64
    SampledAt      time.Time
    Err            error   // non-nil == this sample failed
}

type PressureSource interface { Sample() Pressure }
```

`PressureSource` is an interface specifically so deterministic tests
inject a fake and never touch a real filesystem or sleep (C2).

### 6.2 Disk headroom (standard library only)

`internal/storage` gains:

```
// diskusage_unix.go        //go:build unix
func DiskUsage(path string) (freeBytes, totalBytes uint64, err error)  // syscall.Statfs

// diskusage_unsupported.go //go:build !unix
func DiskUsage(path string) (uint64, uint64, error) { return 0, 0, ErrDiskUsageUnsupported }
```

`syscall.Statfs` is standard library, so
[`docs/dependencies.md`](dependencies.md)'s zero-external-dependency
policy is untouched. Per
[`docs/support-matrix.md`](support-matrix.md), only Linux amd64 is
actually tested; the `unix` tag covers Linux and Darwin, and Windows
gets the unsupported stub.

**Resolved: what an unsupported platform does.** Fail-closed applied at
the *right* moment — configuration time, not request time:

- If `-disk-pressure-threshold` or `-disk-critical-threshold` is set on
  a platform where `DiskUsage` returns `ErrDiskUsageUnsupported`, the
  node **refuses to start**, naming the flag and the platform.
- If neither is set, disk-pressure admission is simply off (`v0.5.0`
  behavior exactly) and `/status` reports
  `diskPressure: "unsupported"`, so an operator is never misled into
  believing protection is active.
- If the probe worked at startup and later *fails* at runtime (`EIO`,
  unmounted path), that is a runtime fault and the fail-safe direction
  applies: the node enters `LowSpace` and admission tightens until
  sampling recovers, with `chronicledb_disk_probe_failures_total`
  incrementing. Rationale: a storage layer that has stopped answering
  questions about itself is not one to accept more writes against.

### 6.3 Memory

`runtime/metrics` (standard library) sampled on the same cadence,
reading `/memory/classes/heap/objects:bytes` and
`/memory/classes/total:bytes`, compared against `-max-heap-bytes`
(default `0` = disabled). `runtime.ReadMemStats` is deliberately **not**
used: it can stop the world, which on this codebase's single event loop
is exactly the pause we are trying to avoid.

`docs/admission-control.md` must state plainly that Go provides no hard
heap cap, that `-max-heap-bytes` is an *admission* threshold and not an
allocator limit, and that `GOMEMLIMIT` is the real mechanism an
operator should also set. Overstating this would be the kind of claim
[`docs/roadmap.md`](roadmap.md) §Maturity Model forbids.

### 6.4 From pressure to admission: three states, with hysteresis

| State | Entered when | Lane B writes | Lane B reads | Lane A | Lane K |
|---|---|---|---|---|---|
| `Normal` | headroom ≥ `threshold × 1.1` and heap OK | full `MaxConcurrent` | full | full | unaffected |
| `LowSpace` | `DiskFreeBytes < -disk-pressure-threshold`, or `HeapBytes > -max-heap-bytes`, or probe error | `SetEffectiveConcurrent(max(1, MaxConcurrent/4))` | full | full | unaffected |
| `Critical` | `DiskFreeBytes < -disk-critical-threshold` | **all rejected**, reason `disk_critical` | full | full | unaffected |

- Thresholds accept an absolute size (`2GiB`) or a percentage of
  `DiskTotalBytes` (`10%`). `-disk-critical-threshold` must be strictly
  less than `-disk-pressure-threshold` or startup fails.
- **De-escalation requires 10% hysteresis** (`headroom ≥ threshold ×
  1.1`) so a node does not flap between states on every poll while a
  workload hovers at the boundary. Flapping is not merely noisy: each
  transition is an audited health event (§20.3).
- Entering `LowSpace` or `Critical` **triggers an immediate GC pass
  proposal** if GC is enabled (§14.5) — the one automatic action
  pressure takes, and it deletes only what `docs/mvcc.md` §6 already
  permits (C3).
- **Lane K is never affected by any state.** A follower under
  `Critical` still appends and still votes. If its disk is genuinely
  full the append fails and the existing `Node.fail` path halts that
  node explicitly (`DURABILITY`) — a correct and already-proven
  outcome, not something admission may pre-empt by silently refusing
  consensus work.

## 7. Snapshot and backup resource limits (A-6)

- **Backup** is Lane **A2** (§3.2a) and additionally **serialized to
  one at a time** per node by its own dedicated single-slot gate
  inside `Node`. A second concurrent `/admin/backup` gets `503`
  `admin_operation_in_progress`, not a queue slot — two concurrent
  exports both run on the event loop anyway, so queueing them only
  hides the cost.
- **Scrub** is Lane **A2**, serialized the same way, and additionally
  I/O-rate-limited by `-scrub-bytes-per-sec` (default 64 MiB/s, `0` =
  unlimited) so a scrub cannot saturate the disk the commit path needs
  (§21.4).
- Neither ever holds a Lane A1 slot, so neither can delay a
  membership change, an upgrade finalize, or a TLS reload (Rule CP-3).
- **Snapshot creation** stays threshold-driven and on the event loop
  (§4.4), with the pre-emptive heartbeat and the duration histogram.
- **GC** is not an I/O consumer (it frees memory and shrinks future
  snapshots), but its Apply-time work is bounded per pass by **two**
  numbers — `-gc-max-versions-per-pass` (versions *removed*) and
  `-gc-max-keys-per-pass` (keys *examined*) — both carried *in the
  command* so the bound is identical on every replica (§14.4).
  Bounding only removals would leave the walk itself `O(total keys)`;
  §14.4 explains why both are required.

## 8. Rejection semantics and the stable error contract

### 8.1 Go-level contract

- Sentinel: `admission.ErrOverloaded`. Every rejection satisfies
  `errors.Is(err, admission.ErrOverloaded)`.
- Concrete: `*admission.RejectedError`, carrying `Reason` and
  `RetryAfter`, retrievable with `errors.As`.
- **A rejection is never an `fsm.Outcome`.** `Node.Propose` returns
  `(fsm.Outcome{}, err)` — the same shape as `*NotLeaderError` —
  because a rejected request has no outcome, by definition. This is
  the Go-level statement of `REJECTION SAFETY`.

### 8.2 The `Reason` vocabulary (stable, documented, operator-scriptable)

Following the precedent [`docs/membership.md`](membership.md) set with
its fixed `reason` strings:

| `Reason` | Meaning | `Retry-After` |
|---|---|---|
| `queue_full` | The gate's waiting room was full | 1s |
| `queue_timeout` | Waited `MaxWait` without a slot | 1s |
| `concurrency_limit` | An event-loop ceiling fired: `len(n.waiters)` (§5.3) or `len(n.pendingReads)` (§9.1) | 1s |
| `read_lease_limit` | The live read-lease ceiling `-max-live-read-leases` was reached (§9.1, §15.3) | 1s |
| `disk_pressure` | `LowSpace`; tightened ceiling reached | 5s |
| `disk_critical` | `Critical`; all client writes refused | 30s |
| `memory_pressure` | `-max-heap-bytes` exceeded | 5s |
| `admin_operation_in_progress` | A Lane A single-slot operation is busy | 10s |
| `shutting_down` | Node is stopping | none (do not retry here) |

New reasons may be added in a MINOR release; existing ones never change
meaning. A client must treat an unknown reason as retryable if `503`
was returned.

### 8.3 HTTP contract

```
HTTP/1.1 503 Service Unavailable
Retry-After: 1
Content-Type: application/json

{"error":"admission: overloaded (queue_full)","reason":"queue_full","retryable":true}
```

Distinctness, stated because it is the whole point of a "stable error
contract":

| Condition | Status | Body marker |
|---|---|---|
| Overload / capacity | **`503`** | `reason` from §8.2 |
| Not leader | `409` (unchanged) | `leaderHint` |
| SI write-write conflict | `200` (unchanged) | `status: "ABORTED"` |
| Snapshot older than the GC horizon (§15) | `200` | `status: "ABORTED_STALE"` |
| Malformed request | `400` (unchanged) | `error` |
| AuthN / AuthZ failure | `401` / `403` (unchanged) | — |

A `503` therefore never overlaps a correctness outcome, and a client
can distinguish "try again, nothing happened" from "this transaction
lost a conflict" from "your snapshot aged out" with no ambiguity.

### 8.4 Why a rejection is always safe to retry

`REJECTION SAFETY` (§27.3) follows from one structural fact: every gate
acquisition in §5.4 happens **before** the request reaches `proposeCh`,
and therefore before `raft.Core.Step(InputPropose)`, and therefore
before any log index is allocated, any byte is appended, or any
`RequestID` is recorded. A rejected request is indistinguishable, in
every durable and replicated artifact, from a request that was never
made. Proof obligation: AC-8 drives a 50%-rejection workload with
recycled `RequestID`s and asserts, via `internal/oracle`, zero
duplicate effects and zero `RequestID`s with two different outcomes.

## 9. Interaction with every other subsystem

### 9.1 ReadIndex

`BeginReadIndex` is Lane B (`readGate`). Two things must not change:

- The `readGate` slot is released when `BeginReadIndex` *returns*, not
  when the transaction ends. Holding a slot for a whole transaction
  would let a long-running, well-behaved reader consume admission
  capacity indefinitely.
- `checkPendingReads` and the `sentSeqCounter`/`ackSeq` machinery are
  Lane K and gain no gate. A pending read already accepted into
  `n.pendingReads` is never retroactively rejected for capacity:
  admission decides at the door, never after.

### 9.1a Two event-loop ceilings the read path must gain

Releasing the gate slot at the door is correct, but it means the gate
does **not** bound the per-node state a read leaves behind. Two sets
outlive their gate slot and neither is capped at `481ff93`:

- `n.pendingReads` (fact 8c) — a caller that cancels its context
  returns from `BeginReadIndex` and frees its slot, but its entry
  stays until the read resolves or leadership is lost. And
  `checkPendingReads` iterates the whole slice after **every**
  `processOutput`, so its cost is on Lane K's critical path.
- the live read-lease map (§15.3) — new in this release, held for a
  whole transaction by design, and scanned for `minLease` on every GC
  tick.

Counterexample, which is why neither may be left uncapped: a leader
in a minority partition stays leader (no higher term reaches it) and
resolves **no** reads, because no quorum acks its forced round. Each
`BeginReadIndex` appends a `pendingRead` and forces a fresh
`AppendEntries` to every peer (`internal/node/node.go:1478`). Callers
time out after 1 s, release their `readGate` slots, and new callers
are admitted immediately. `len(n.pendingReads)` grows without bound,
and per-inbound-Raft-message cost grows linearly with it — client read
concurrency becomes a term in Lane K's service time, which §4.3
states it is not. C1 forbids exactly this shape of hidden queue.

**Decision: two ceilings, both checked in `handleReadIndex`, on the
event-loop goroutine, before anything is appended** — the read-side
twin of §5.3's `waiters` check, and fail-safe for the same reason:

```
if len(n.pendingReads) >= n.maxPendingReads {
    req.resultCh <- readResult{err: &admission.RejectedError{
        Reason: admission.ReasonConcurrencyLimit, RetryAfter: time.Second}}
    n.metrics.AdmissionDefenseRejectionsTotal.Inc()
    return
}
if n.leases.Len() >= n.maxLiveReadLeases {
    req.resultCh <- readResult{err: &admission.RejectedError{
        Reason: admission.ReasonReadLeaseLimit, RetryAfter: time.Second}}
    return
}
```

- `maxPendingReads` is set from `-max-concurrent-reads`, exactly as
  `maxClientWaiters` is set from `-max-inflight-proposals`. It bounds
  `checkPendingReads`'s per-message cost by a configured constant.
- `maxLiveReadLeases` is set from the new `-max-live-read-leases`
  (default `4096`, §10.1). It bounds the lease map, which outlives
  pending reads.
- A lease-limit rejection increments the ordinary
  `chronicledb_admission_rejected_total{gate="read",reason="read_lease_limit"}`,
  **not** the defense counter: unlike the `waiters` and
  `pendingReads` ceilings, it has no caller-side gate counterpart, so
  it is the primary limiter for that resource rather than a backstop.

**`minLease` must not be an O(n) scan.** With the ceiling in place an
`O(n)` scan per GC tick is bounded, but it is still `O(live leases)`
work on the event loop for a value the loop can maintain
incrementally. Required: the lease registry keeps `StartSeq`s in a
counted ordered multiset (a sorted `StartSeq → count` map, or a
min-heap with lazy deletion), so `minLease` is `O(1)`, registration
and release are `O(log n)`, and the GC tick's cost does not depend on
how many readers are open. Proof obligation AC-21.

Both ceilings are also the answer to "no unbounded hidden queue"
(C1) for the read path: after `v0.6.0`, the total per-node state a
client can cause on the read side is
`-max-concurrent-reads + -admission-queue-depth` goroutines,
`-max-concurrent-reads` pending reads, and `-max-live-read-leases`
leases — three capacities, no policies.

### 9.2 SQL

`internal/sql` gains one `*admission.Gate` on `Engine`/`Session`
(`sqlGate`, `-max-concurrent-sql-statements`, default 256), acquired
per statement execution in `exec.go` and released on completion.

- In **replicated** mode this is *in addition to* the node's gates,
  and that is intentional: the SQL gate bounds parser/planner/scan work
  (which `Node` never sees), while the node gates bound Raft work.
  Nested acquisition across two independent gates cannot deadlock
  because the order is always sql → node and never the reverse.
- In **standalone** mode the SQL gate is the only gate that exists
  (standalone mode has no `Node`). `docs/admission-control.md` must say
  so explicitly rather than letting a library user assume node-level
  protection they do not have.
- `ScanPrefix` (`internal/sql/engine.go`) materializes a full
  `mvcc.Store.Export()` for a prefix scan. **`v0.6.0` moves it off
  `Export` entirely** — see §15.2a, which is a `GC SAFETY`
  requirement, not an efficiency one. Under the SQL gate the
  replacement `ScanVisible` call is bounded to
  `-max-concurrent-sql-statements` simultaneous materializations.
  Sizing guidance goes in the operator doc.

### 9.3 Transactions and idempotency

Unchanged. `IDEMPOTENCY` and `REQUEST OUTCOME STABILITY` hold because
admission never records anything (§8.4), and because the gate sits
strictly outside `fsm.Apply`.

### 9.4 Snapshots and backup

Covered in §7. One additional rule: `handleInstallSnapshot` (a
*follower* receiving a snapshot) is Lane K and is never gated —
refusing a snapshot install for local capacity reasons would strand a
lagging follower permanently, converting a transient local condition
into a permanent membership problem.

### 9.5 Membership

Lane A1 (control). Three specific interactions must be tested (A-14):

- A saturated client workload must not delay or fail
  `AddLearner`/`PromoteToVoter`/`RemoveServer` (AC-12).
- `ErrConfirmationRequired`, `ErrLearnerNotCaughtUp`, and
  `ErrNodeRemoved` keep their exact existing semantics and status
  codes; an admission rejection is a *fourth*, distinct outcome and
  never masquerades as one of them.
- A learner catching up receives `AppendEntries`/`InstallSnapshot` on
  Lane K, so catch-up progresses at full speed while the cluster is
  under client overload.
- A running backup **and** a running scrub together must not delay a
  membership change either: they are Lane A2, membership is Lane A1,
  and Rule CP-3 keeps the capacities disjoint. AC-22 proves it.

### 9.6 Upgrades

Lane A1 (control). `UpgradePrecheck`/`FinalizeUpgrade` must remain callable under
overload — an operator's response to a sick cluster must not be
sheddable. `FinalizeUpgrade`'s internal `upgradePrecheck` call does not
re-acquire (§5.4); this is a real deadlock the plan names in advance.

### 9.7 Restart and failover (A-14)

- **Restart**: all admission state is in-memory and per-process; a
  restart resets every gate to empty. Consistent with
  [`docs/observability.md`](observability.md) §7's existing rule that
  counters reset on restart. Nothing about admission is persisted, and
  nothing about it is replicated.
- **Failover**: a new leader begins with `waiters` empty and gates
  empty, so it inherits no stale count. The deposed leader's
  outstanding proposals are resolved with `ErrLeadershipLost` by the
  existing `out.SteppedDown` path, and each resolution runs the
  caller's `defer release()`. AC-11 asserts that after a failover under
  saturation and a quiescence period, every gate's `InFlight() == 0` on
  both old and new leader — i.e. no token leak.

### 10.3 Default-selection discipline

Every default above must be justified in
`docs/admission-control.md` / `docs/storage-lifecycle.md` against
either (a) the memory arithmetic in §5.2, or (b) "exactly the
pre-`v0.6.0` behavior." Defaults that are neither are not acceptable —
this project does not ship a number because it looks reasonable. In
particular:

- `-max-inflight-proposals=256` is justified by §5.2's 512 MiB
  worst-case figure and must be re-derived against a measured
  `internal/benchutil` run before the release gate (§31, gate 6).

- **The three GC rate flags are not free choices.** `-gc-interval`,
  `-gc-min-advance-seqs` and `-gc-max-versions-per-pass` jointly cap
  how fast GC can reclaim:

  ```
  reclaim_rate ≈ gc-max-versions-per-pass
                 ÷ max(gc-interval, time to commit gc-min-advance-seqs entries)
  ```

  (with §13.4's continuation passes, which are what make the
  denominator `gc-interval` rather than "one pass per watermark
  advance"). If `reclaim_rate` is below the workload's
  version-creation rate, `chronicledb_mvcc_versions` grows
  monotonically **with GC enabled and correctly implemented**, and
  SL-19 — a required gate-2 item — fails. These three values
  therefore affect *release acceptance*, so they are not
  implementation-time choices: §35.1 excludes them, and gate 6
  requires all three to be derived from the measured version-creation
  rate of SL-19's own workload, recorded in
  [`docs/benchmarks.md`](benchmarks.md) alongside the admission
  figures.

- `-gc-max-keys-per-pass=16384` is a *work* bound, not a rate bound:
  any value ≥ 1 is safe and deterministic (it is carried in the
  command), and it affects only how many commands a full keyspace
  walk takes. It stays an implementation-time choice, justified in
  the operator doc against measured Apply cost.
- `-gc-interval=0`, `-snapshot-retain-count=1`,
  `-wal-retain-extra-segments=0`, and both `-disk-*-threshold` flags
  are all "exactly `v0.5.0`": `v0.6.0` changes no observable behavior
  unless an operator opts in, with the single exception in §10.4.

### 10.4 The one behavior change that is on by default

HTTP server timeouts and the connection caps are **on by default**,
because "no timeouts at all" is not a behavior worth preserving
compatibility with. This is called out in `CHANGELOG.md` and
[`docs/upgrades.md`](upgrades.md) as the single default-behavior change
in `v0.6.0`: a client holding an idle connection longer than
`-http-idle-timeout`, or streaming a request body for longer than
`-http-read-timeout`, will now be disconnected.

## 12. What actually consumes disk, and therefore what "reclamation" means

Measured against the tree, a node's `DataDir` contains exactly:

| Consumer | Grows with | Reclaimed by | Bounded today? |
|---|---|---|---|
| WAL segment files | every appended log entry and HardState record | `WAL.CompactBefore` after a durable snapshot | **Yes** — bounded by `-snapshot-threshold` plus the current segment |
| Snapshot file(s) | size of live FSM state | `Manager.pruneExcept` | **Yes** — exactly one file |
| Audit log | admin actions | nothing | No — out of scope, §28.3 |
| `snapshot/tmp` | in-progress writes | `NewManager` on restart | Yes |

**Therefore:** the thing that actually grows without bound in
ChronicleDB today is not a file — it is **FSM state in RAM**, which
then makes each successive snapshot file larger. Two components grow:

1. **MVCC version chains** (`mvcc.Store.chains`) — every version ever
   committed, forever. This is what GC fixes.
2. **The `RequestID` outcome table** (`fsm.outcomes`) — one entry per
   distinct `RequestID`, forever. GC does **not** fix this, and
   `v0.6.0` deliberately does not try to (§28.2). It is measured
   instead.

This is the first substantive deviation from
`enterprise-v1-plan.md` §10's literal text, which speaks of
"storage-layer file-space reclamation for fully-superseded MVCC data."
There is no MVCC file. The accurate statement, which `v0.6.0`
implements and `docs/storage-lifecycle.md` must carry, is:

> **MVCC GC reclaims memory immediately and disk at the next snapshot
> boundary.** It never rewrites a file, because MVCC data has never
> been stored in one.

Recorded as deviation D1 in §26.

## 13. MVCC GC: the determinism decision (the central choice of this release)

### 13.1 The problem, stated exactly

[`docs/invariants.md`](invariants.md) `DETERMINISM BOUNDARY` names
`internal/mvcc` in its scope. `STATE MACHINE SAFETY`'s proof obligation
is that independently constructed replicas fed the identical committed
history reach byte-identical state, and `internal/fsm`'s
`TestEncodeStateDeterministic` enforces exactly that today.

[`docs/mvcc.md`](mvcc.md) §6 defines `GCWatermark` as *"the smallest
`StartSeq` among all currently active transactions' snapshots."*
Active transactions are a **local, per-process, wall-clock-dependent**
fact. If each node reclaimed versions using its own local watermark:

- two replicas with identical committed histories would hold different
  version chains and produce different snapshot bytes, breaking
  `STATE MACHINE SAFETY`'s stated proof obligation and
  `TestEncodeStateDeterministic`;
- a follower (which has *no* active transactions, so its watermark
  would be "latest applied `CommitSeq`") would reclaim far more
  aggressively than the leader, and a later failover onto that node
  would silently expose the more-aggressively-GC'd state to readers;
- the `internal/oracle` reference model and every deterministic replay
  test would lose their meaning for the MVCC layer.

### 13.2 Decision: **GC is replicated state**

> The GC watermark is advanced only by a committed Raft log entry, and
> all reclamation happens inside `fsm.Apply` as a pure, deterministic
> function of that entry and prior FSM state.

The nondeterministic input (which transactions are open, how much disk
is left, what time it is) is computed **outside** the boundary, on the
leader, and enters the state machine as an explicit command field —
which is exactly the escape hatch `DETERMINISM BOUNDARY` already
specifies: *"nondeterministic values are generated outside the
deterministic core and passed in as explicit inputs when required."*
This is the identical pattern `SetClusterVersionCommand` already uses
for `FinalizeUpgrade`.

Consequences, all accepted:

- One new FSM control-command kind (§16.1).
- One new cluster generation, **3** (§24).
- FSM state gains four fields (`gcWatermark`, `gcCursor`, `gcPasses`,
  `gcPassSeq`), encoded in a generation-3-gated additive trailing
  block (§16.2).
- GC becomes cluster-wide and uniform: every replica reclaims the same
  versions at the same log index.

### 13.3 Rejected alternative: local, non-replicated GC

Reclaim locally on each node using each node's own watermark, and
weaken `STATE MACHINE SAFETY` from "byte-identical" to "equivalent
visible state."

**Rejected.** It is *arguably* visibility-safe, but: it destroys the
byte-identical-snapshot property that `TestEncodeStateDeterministic`,
the `internal/oracle` model, and the whole deterministic-replay
discipline rest on; it makes `GC SAFETY` a property each node must
establish separately rather than one the log establishes once; and it
gives a snapshot transferred by `InstallSnapshot` a GC state unrelated
to the receiver's. This project's entire testing strategy is built on
the determinism boundary; trading it for one avoided generation bump is
a bad trade, and it is precisely the sort of "small correctness
loophole for convenience" [`docs/vision.md`](vision.md)'s guiding
principle rules out. Recorded in ADR-0020 as the rejected option.

### 13.4 The watermark the leader proposes

On each `-gc-interval` tick, **on the leader only**, on the event-loop
goroutine:

```
minLease = min StartSeq over live read leases (§15.3); +inf if none
applied  = the FSM's highest applied CommitSeq
floor    = applied - gc-min-retain-seqs           (saturating at 0)
W        = min(minLease, applied, floor)

advance    := W > f.gcWatermark + gc-min-advance-seqs
continue   := f.gcCursor != ""          // the walk at the current
                                        // watermark is unfinished
propose iff (advance || continue) && no GC proposal is already in flight
    Watermark   = max(W, f.gcWatermark)   // never proposes a decrease
    MaxVersions = -gc-max-versions-per-pass
    MaxKeys     = -gc-max-keys-per-pass
    RequestID   = "\x00chronicledb-gc\x00w=<Watermark>\x00p=<f.gcPassSeq>"
```

- `min(minLease, applied)` is **exactly `docs/mvcc.md` §6's rule**
  ("smallest `StartSeq` among active transactions, or the most recent
  applied `CommitSeq` if none active"). Unchanged, as S-1 requires.
- `floor` is an **additional** conservatism this plan adds; §14.2
  explains why it is required rather than optional.
- Only the leader proposes; a follower never does. The log linearizes
  watermark advances by construction, so no `SERIALIZED MEMBERSHIP
  CHANGE`-style concurrency machinery is needed.

### 13.4a Resolved: continuation passes, and why the `RequestID` must carry `gcPassSeq`

An earlier draft proposed only when the watermark advanced, and keyed
the `RequestID` on `(W, MaxVersions)` alone. That combination caps
reclamation at `MaxVersions` versions **per watermark advance**,
because a second command at the same `W` would compute the identical
`RequestID`, hit `controlOutcomes`' idempotency short-circuit (the
same one `ApplySetClusterVersion` uses at
`internal/fsm/clusterversion.go:186`), and reclaim nothing.

Counterexample under the §10.2 defaults: with
`-gc-min-advance-seqs=256` and `-gc-max-versions-per-pass=4096`, a
workload committing 32-mutation transactions creates
`256 × 32 = 8192` versions per watermark advance against a ceiling of
4096 reclaimed. Version count grows monotonically with GC enabled and
correctly configured, and SL-19 fails with no operator knob that
fixes it.

Two changes close it, and both are required:

1. **`continue`**: the leader proposes again while `f.gcCursor != ""`,
   i.e. while the sorted walk at the current watermark is unfinished,
   even though the watermark itself has not moved. `gc-min-advance-seqs`
   gates *advances*, not *continuations*.
2. **`gcPassSeq` in the `RequestID`**: `f.gcPassSeq` is a new
   monotone `uint64` in FSM state, incremented by every applied
   `AdvanceGCWatermark`. The leader reads it from its own applied FSM
   when building the command, so successive continuation passes get
   distinct `RequestID`s while a **retry of the same pass** — after a
   leader crash mid-propose, or a replayed log entry — reproduces the
   identical `RequestID` and is idempotent through `controlOutcomes`
   exactly as `FinalizeUpgrade` is.

The "no GC proposal already in flight" condition is what makes
`f.gcPassSeq` predictable on the leader: at most one
`AdvanceGCWatermark` is outstanding at a time, tracked by a single
boolean on the event-loop goroutine, cleared when the proposal
resolves (applied, superseded, or leadership lost). If a proposal's
outcome is unknown because leadership was lost, the next leader
simply reads its own applied `f.gcPassSeq` and proceeds — no
cross-term coordination is needed, because the `RequestID` is a
function of replicated state only.

## 14. The GC rule and its bounded, deterministic application

### 14.1 The reclamation predicate (verbatim from `docs/mvcc.md` §6)

A version `(CommitSeq=c)` of key `K` may be removed **iff** there
exists a version `(CommitSeq=c')` of the same `K` with
`c < c' <= W`, where `W` is the applied GC watermark. The newest
version of `K` is never removed. Nothing else is ever removed.

### 14.2 Why the lag floor is required, not optional

The leader's `minLease` only covers transactions **this leader** knows
about. It cannot cover:

- transactions opened on a *previous* leader that are still live on
  that (now-follower) process and still reading locally;
- any reader whose `StartSeq` was obtained immediately before a
  failover.

So a watermark based on `minLease` alone is not sound across a
leadership change. Two mechanisms close the gap, and **both** are
required:

1. **The lag floor** (`-gc-min-retain-seqs`) makes the unsound window
   quantitative and small: a transaction must be more than
   `gc-min-retain-seqs` commits old before it can possibly be affected.
2. **The horizon guard** (§15) makes the property *unconditional*: any
   read or commit whose `StartSeq` is below the applied watermark is
   refused, loudly. This is what turns "usually fine" into an
   invariant.

### 14.3 Tombstones

No special case, per S-3. A tombstone is a version; it is reclaimable
under exactly the predicate above, and the newest version of a key —
tombstone or not — is never removed. Consequence, which
`docs/storage-lifecycle.md` must state: **deleting every key in the
database does not shrink the key count.** One tombstone per
ever-written key remains forever. Reclaiming the final tombstone of a
key requires a "key is fully absent" notion `docs/mvcc.md` §7
deliberately does not have; it is deferred (§28.2), not silently
skipped.

### 14.4 Bounded, resumable, deterministic application

Reclamation must not scan every key on the event loop. `fsm.Apply` for
an `AdvanceGCWatermarkCommand`:

```
0. if prior, ok := f.controlOutcomes[cmd.RequestID]; ok { return prior }
       // idempotent replay, exactly ApplySetClusterVersion's step

1. f.gcWatermark = max(f.gcWatermark, cmd.Watermark)
       // monotone; a lower cmd.Watermark is a deterministic no-op

2. W := f.gcWatermark                  // AUTHORITATIVE — see below
   removed, examined := 0, 0
   for k := range f.store.KeysFrom(f.gcCursor, cmd.MaxKeys) {
       removed += f.store.ReclaimKey(k, W, cmd.MaxVersions-removed)
       examined++
       if removed >= cmd.MaxVersions { break }
   }

3. f.gcCursor = the next key after the last one examined, or "" with
   f.gcPasses++ if the walk reached the end of the key set

4. f.gcPassSeq++

5. f.controlOutcomes[cmd.RequestID] = Outcome{Status: StatusCommitted,
                                              CommitSeq: index}
   f.store.SetGCWatermark(W)
   return that outcome
```

**Resolved: the predicate compares against the post-`max()`
`f.gcWatermark`, never against `cmd.Watermark`.** Step 2's `W` is
`f.gcWatermark` *after* step 1. Both choices are deterministic, so
this is not a `GC DETERMINISM` question — it is a question of how
many distinct horizons exist in the system, and the answer must be
one:

- `f.gcWatermark` is the value the read-side guard refuses below
  (§15.2), the value the commit-side check uses (§15.4), and the
  value encoded into snapshots (§16.2). Reclaiming against
  `cmd.Watermark` when it is *lower* would reclaim against a horizon
  narrower than the one readers are refused at — harmless, but it
  would mean the horizon that governs deletion and the horizon that
  governs visibility are two different numbers that only usually
  agree.
- With the post-`max()` rule, a replayed or out-of-order lower
  watermark is a no-op in **both** senses simultaneously: it neither
  lowers the horizon nor reclaims against a stale one.

This rule is stated identically in ADR-0020's Decision, in §27.5/§27.6,
and in every pseudocode fragment in this document. SL-4a asserts it
directly: a command whose `Watermark` is below `f.gcWatermark`
reclaims exactly what the *current* watermark permits, not what the
command's lower value would have permitted.

**Resolved: the per-pass bound is on work, not only on removals.** An
earlier draft bounded only `cmd.MaxVersions` (versions *removed*).
That leaves the walk itself `O(total keys)`: if nothing is
reclaimable, Apply examines the entire key set before it can stop.
And because `mvcc.Store.chains` is a bare `map[string][]Version` with
no ordered index (fact 8b), "walk keys in ascending string order"
naively means sorting the whole key set on every Apply.

Counterexample: 10M keys, each written exactly once, so no version is
reclaimable anywhere. Every GC tick's Apply materializes and sorts a
10M-element key slice, walks all 10M chains, removes zero versions,
and wraps — a multi-second event-loop block, on **every replica**,
every `-gc-interval`. That is exactly the `O(total keys)` walk
ADR-0020 alternative 4 rejects.

Two requirements close it:

1. **`cmd.MaxKeys` bounds keys examined**, alongside `cmd.MaxVersions`
   bounding versions removed. Both are carried in the command
   (below), so the work every replica does is identical and is a
   function of the log, not of local flags.
2. **`mvcc.Store` must provide ordered key access whose cost is
   independent of the total key count.** The store gains
   `KeysFrom(cursor string, limit int) []string`, returning at most
   `limit` keys in ascending order strictly after `cursor`, and it
   **must not** sort or scan the whole key set to do so. Acceptable
   implementations: a maintained sorted key slice with binary-search
   insertion, a B-tree, or a skip list. A per-Apply full sort is
   explicitly forbidden. Whichever structure is chosen, the cost it
   adds to the *write* path (`ApplyCommit` inserting a
   previously-unseen key) must itself be measured and recorded at
   gate 6, because that cost is the price of this fix.

   Note the key set never shrinks under GC — §14.1 never removes a
   key's newest version — so the index needs insertion and ordered
   traversal but no deletion.

   Proof obligation **SL-2b**: with `MaxKeys`/`MaxVersions` fixed,
   `ApplyAdvanceGCWatermark`'s wall-clock cost and allocation count
   are flat as the total key count grows 10×, measured through
   `internal/benchutil`. A full-sort implementation fails it.

`MaxVersions` **and** `MaxKeys` are carried in the command, not read
from local config, so two nodes with different
`-gc-max-versions-per-pass` / `-gc-max-keys-per-pass` flags still
perform byte-identical work. This is load-bearing: it is the
difference between a deterministic Apply and a config-dependent one.

`RequestID` is `"\x00chronicledb-gc\x00w=<W>\x00p=<gcPassSeq>"`
(§13.4a), mirroring `FinalizeUpgrade`'s deterministic-`RequestID`
pattern, so a retry after a leader crash mid-propose is idempotent
through the existing `controlOutcomes` table rather than a second
ad-hoc mechanism — while successive continuation passes at an
unchanged watermark remain distinct commands.

### 14.5 Triggering

- Periodic: `-gc-interval`, on the leader.
- Pressure-driven: entering `LowSpace`/`Critical` (§6.4) triggers one
  immediate evaluation. This is the only automatic reaction to disk
  pressure, and it deletes nothing beyond §14.1's predicate (C3).
- Never on a follower; never during a leadership transition (the tick
  simply finds `Role != Leader` and does nothing).

### 14.6 Standalone mode: GC is not implemented there, and this is deliberate

`internal/txn.Manager` (standalone/embedded mode) does **not** run GC
in `v0.6.0`.

Reasons, in order of weight:

1. Standalone mode has **no cluster generation** — the entire
   generation-gating mechanism (`internal/version`,
   `SetClusterVersion`) exists only in replicated mode. Introducing a
   new durable record kind into a standalone WAL with no generation
   gate would create exactly the silent-format-misinterpretation hazard
   `NO SILENT FORMAT MISINTERPRETATION` forbids: a `v0.5.0` binary
   opening a `v0.6.0` standalone data directory.
2. `Manager.recover` (`internal/txn/txn.go:147`) calls
   `fsm.DecodeCommitTxn` unconditionally on **every** replayed record.
   Adding a control record to that log changes recovery semantics for a
   mode that has no upgrade story at all.
3. Standalone mode is explicitly a Go-library surface
   ([`docs/sql.md`](sql.md) §8), not a deployed database.

The horizon guard (§15) is still compiled into `internal/mvcc` in
standalone mode; with the watermark permanently 0 it can never fire.
`docs/storage-lifecycle.md` and `docs/mvcc.md` §6 must both state that
GC is a replicated-mode capability in `v0.6.0`. Deviation D2 in §26.

## 15. Snapshot-horizon enforcement (what makes `GC SAFETY` unconditional)

### 15.1 Why refusal is mandatory, not a nicety

Suppose version `c` of key `K` was reclaimed because some `c'` exists
with `c < c' <= W`. A transaction `T` with `StartSeq = S` where
`c <= S < c'` is *entitled* to see `c`. After reclamation,
`Store.Visible(K, S)` returns the newest surviving version `<= S`,
which is some `c'' < c` — or nothing at all.

That is not a missing row. It is `T` reading a **different, older,
committed value than Snapshot Isolation specifies**, with no error. A
silent SI violation is strictly worse than an abort. Therefore refusing
`S < W` is a correctness requirement, not a convenience.

The bound is exact: harm requires `c <= S < c' <= W`, hence `S < W`;
and no snapshot with `S >= W` can ever be harmed. Refusing exactly
`S < W` is sufficient, and only marginally conservative.

### 15.2 Where the guard lives: structurally, inside `internal/mvcc`

Not in `internal/txn`, not in `internal/sql`, not in `internal/node` —
in the one place every read must pass through:

```
var ErrSnapshotTooOld = errors.New("mvcc: snapshot older than the GC horizon")

func (s *Store) Visible(key string, startSeq uint64) (value []byte, found bool, err error)
func (s *Store) ScanVisible(prefix string, startSeq uint64) ([]KV, error)
func (s *Store) SetGCWatermark(w uint64)   // §15.2b: fsm.Apply AND state restore
func (s *Store) GCWatermark() uint64
func (s *Store) KeysFrom(cursor string, limit int) []string   // §14.4
func (s *Store) ReclaimKey(key string, w uint64, budget int) int
```

`Visible` gains an `error` return and checks `startSeq < s.gcWatermark`
under the same `RLock` that reads the chain — so the check and the read
are one atomic instant, with no window in which a concurrent watermark
advance lets a stale read slip through. Changing the signature is a
mechanical call-site update across `internal/txn/txn.go`,
`internal/sql/engine.go`, and their tests; it is slice 7 in §33 and is
deliberately a *compile error* at every call site rather than a
silently-ignored new field.

`CheckConflicts` is **unaffected** and needs no guard: it reads only
the newest version of each key, which GC never removes. This must be
asserted by a test (SL-4/SL-5), not assumed.

### 15.2a Resolved: the scan path must be moved off `Store.Export`

"The one place every read must pass through" is **not** `Visible`
today. Fact 8a: `internal/sql`'s `mergeScan`
(`internal/sql/engine.go:307`) — reached from `replicatedTxn.ScanPrefix`
(`:236`, `:241`) and `standaloneTxn.ScanPrefix` (`:154`) — calls
`mvcc.Store.Export()` (no `startSeq` parameter, no guard) and then
re-implements the visibility rule locally in `visibleInChain`
(`:344`). A guard placed only on `Visible` is bypassed by every
prefix scan in the product.

This is not a theoretical gap. Concrete counterexample: key `K` has
versions `c=100` and `c'=900`; `W` advances to `1000`, so `c=100` is
reclaimed under §14.1. A transaction with `StartSeq = 500` runs
`SELECT ... WHERE key LIKE 'K%'`. `mergeScan` searches the surviving
chain for the newest version `<= 500`, finds none, and reports the
row as absent — **with no error**. That is precisely the silent
Snapshot Isolation violation §15.1 declares must be impossible,
delivered through the release's own primary SQL read path. Note also
that `ScanPrefix` already returns `([]KV, error)`, so unlike
`Visible`'s new `error` return, nothing about the signature change
forces a call-site conversion: a missed conversion compiles and ships
silently.

**Decision, three parts, all required:**

1. **`mergeScan` is rewritten onto `Store.ScanVisible`.** `ScanVisible`
   performs the prefix filter *and* the per-key visibility search
   *inside* `internal/mvcc`, under the same `RLock` that checks
   `startSeq < s.gcWatermark` — one atomic instant, exactly as
   `Visible` does. `internal/sql`'s local `visibleInChain` helper is
   **deleted**, not kept alongside: a second copy of the visibility
   rule outside the determinism boundary is what made this bypass
   possible in the first place. The merge with the transaction's own
   local write set stays in `internal/sql`, where it belongs.
2. **`Store.Export` becomes snapshot-encoding-only.** Its only
   legitimate caller is `internal/fsm/snapshot.go:73`, which must
   return every version regardless of any horizon. Its doc comment
   says so, and a structural test —
   `TestExportOnlyCalledFromSnapshotEncoding`, the same AST pattern as
   CP-2 — asserts no package other than `internal/fsm` references it.
   This is what keeps the bypass closed against a future re-addition.
3. **SL-6 is scoped to the read *paths*, not to `Store`'s method
   set.** A reflection test over `Store`'s methods would have passed
   on an unused `ScanVisible` while `mergeScan` stayed on `Export`.
   SL-6 therefore drives every committed-read entry point the product
   actually has — `replicatedTxn.Get`, `replicatedTxn.ScanPrefix`,
   `standaloneTxn.Get`, `standaloneTxn.ScanPrefix`, and every exported
   `mvcc.Store` read method — with `startSeq < watermark`, and
   asserts every one of them refuses.

### 15.2b Resolved: the watermark must be restored, not only applied

The watermark lives in two places: `f.gcWatermark` (FSM state,
encoded in the generation-3 trailing block) and `s.gcWatermark`
(inside `mvcc.Store`, where the read guard reads it). An earlier
draft's API comment said `SetGCWatermark` is "called only from
`fsm.Apply`". Implemented literally, that is a silent bypass of
`SNAPSHOT HORIZON ENFORCEMENT`:

`DecodeState` builds the store with `mvcc.RestoreStore(chains)`
(`internal/fsm/snapshot.go:465`), which constructs a **fresh** `Store`
with a zero watermark, and `handleInstallSnapshot` swaps the whole
FSM in wholesale (`internal/node/node.go:2011`). So after a restart
from snapshot, an `InstallSnapshot`, or a backup restore, a node
would run with `f.gcWatermark = W` but `s.gcWatermark = 0` — the
read-side guard disabled until the next `AdvanceGCWatermark` happens
to apply. SL-6 as scoped above would not catch it, because it sets
the watermark explicitly.

**Decision:** `SetGCWatermark` is called from `fsm.Apply`
(§14.4 step 5) **and** from `DecodeState`, on the value decoded from
the generation-3 trailing block, before the `FSM` is returned.
Equivalently — and preferably, because it removes the ordering
hazard entirely — `RestoreStore` takes the watermark as a parameter,
so it is impossible to construct a restored `Store` without one.

The binding property, stated so it can be tested rather than
reviewed:

> `Store.GCWatermark() == FSM.gcWatermark` at every instant, on every
> node, including immediately after `DecodeState`, after
> `handleInstallSnapshot`, and after a backup/PITR restore.

Proof obligations: **SL-13** and **SL-18** assert it after log-replay
catch-up, after `InstallSnapshot`, and after a restore with and
without `-restore-until`; **SL-6a** asserts it as a post-condition of
`DecodeState` over the SL-1 property corpus.

### 15.3 Read leases

`Node.BeginReadIndex` becomes:

```
func (n *Node) BeginReadIndex(ctx context.Context) (startSeq uint64, lease *ReadLease, err error)

type ReadLease struct{ … }
func (l *ReadLease) StartSeq() uint64
func (l *ReadLease) Release()   // idempotent
```

#### Resolved: the lease is registered at *capture*, not at resolution

An earlier draft said leases are "issued in `handleReadIndex`'s
completion path", which is ambiguous — `handleReadIndex` does not
complete the read — and, read as "at resolution", is the weaker of
the two available orderings. The code has two distinct instants:

- **capture**: `handleReadIndex` (`internal/node/node.go:1462`) reads
  `target := n.core.LastIndex()`. This is the value that later
  becomes the caller's `StartSeq`.
- **resolution**: `checkPendingReads` (`:1525`) delivers
  `readResult{startSeq: pr.target}`, possibly many event-loop
  iterations later, once a majority has acked the forced round and
  `n.appliedIndex >= pr.target`.

Registering at resolution would let the watermark overtake an
already-captured boundary: a read whose `target` was captured at
index `S` contributes nothing to `minLease` while it is pending, so
a GC tick in that window computes `W` as if the read did not exist.
The horizon guard still makes that *safe* — the reader is refused
rather than served stale data — but "safe" here means the reader gets
a spurious `ErrSnapshotTooOld` for a snapshot boundary the node had
already handed out. The stronger ordering is available and costs
nothing, so this plan takes it.

**Decision: the lease is created and inserted into the live-lease
registry inside `handleReadIndex`, in the same statement sequence
that captures `target`, before the `pendingRead` is appended.**

Both the registry and the GC tick (§13.4) are mutated and read
exclusively on the event-loop goroutine, so capture and any watermark
computation are serialized by construction — there is no window at
all, not merely a small one. Consequence, which is the point:
**`W <= minLease <= S` holds for every read this leader has captured,
so a read issued against the current leader can never receive a
spurious `ErrSnapshotTooOld`.** The guard remains as the
unconditional backstop for the cross-leader case §14.2 describes.

#### Lease lifecycle, stated exhaustively

| Event | Where | Effect on the registry |
|---|---|---|
| **Registration** | `handleReadIndex`, immediately after `target := n.core.LastIndex()`, before the `pendingRead` append — and after §9.1a's two ceilings | Insert `leaseID → target` |
| **Successful resolution** | `checkPendingReads` delivers `readResult{startSeq, lease}` | No change — the lease is already live and is now owned by the caller |
| **Resolution failure** (`ErrLeadershipLost`, `ErrNodeRemoved`) | `checkPendingReads` / `handleReadIndex`'s early returns | Release immediately, on the loop, at the same point the error is delivered. The caller never sees a lease, so the caller owes nothing |
| **Normal release** | `ReadLease.Release()` → buffered `releaseLeaseCh` → event loop | Delete. Idempotent (`sync.Once` on the caller side, and a missing key is a no-op on the loop side) |
| **Caller cancellation / `ErrNodeStopped`** | `BeginReadIndex`'s `ctx.Done()` and `doneCh` branches | The caller sends its `leaseID` on `releaseLeaseCh` before returning (select on `releaseLeaseCh` / `n.doneCh`), so a read abandoned *after* registration but *before* or *during* resolution still releases. The `leaseID` is allocated by `BeginReadIndex` before the request is sent, precisely so the cancellation path can name it without having received a result |
| **Leadership loss (step-down)** | `processOutput`'s `out.SteppedDown` branch | Pending-read leases are released together with their `pendingRead`s (those reads fail with `ErrLeadershipLost`). **Already-issued leases are kept**: a follower proposes no watermark, so holding them costs nothing, and they are correct again immediately if this node is re-elected |
| **Expiry** | `-read-lease-max-age` sweep on the loop | Delete. Liveness only — see below |
| **Node stop / restart** | `Stop`, and trivially a restart | The registry is in-memory and per-process; it starts empty |

Interaction with pending `ReadIndex` resolution, stated explicitly
because it is the subtle part: a lease exists for the whole interval
`[capture, release]`, which **strictly contains** the interval
`[capture, resolution]` during which the read is pending. There is
therefore never an instant in which a captured-but-unresolved read is
invisible to `minLease`. A pending read that never resolves (the
minority-partition case) holds its lease until the caller cancels or
`-read-lease-max-age` expires it — which is why §9.1a's ceilings
bound both sets, and why they are checked before registration.

- `internal/sql`'s `replicatedTxn` holds the lease and releases it in
  `Commit` and `Abort`; `Session` releases on close. Every exit path
  must release — enforced by a `-race` leak test (SL-23).
- **A leaked lease stalls GC; it never makes GC unsafe.** That is the
  fail-safe direction, stated as a property.
- `-read-lease-max-age` force-expires a lease so a crashed client
  cannot stall GC forever. This is a **liveness** mechanism only (C2):
  expiring a lease authorizes reclaiming nothing the horizon guard
  would not already protect, because the guard refuses the affected
  transaction regardless of lease state.
- The registry keeps `StartSeq`s in a counted ordered multiset so
  `minLease` is `O(1)` (§9.1a), not an `O(live leases)` scan on the
  event loop.

### 15.4 Commit-side refusal

`fsm.Apply` for a `CommitTxnCommand`, in order:

1. Idempotency (existing `outcomes` lookup and fingerprint check) —
   **first**, so a retry of an already-decided request still returns
   its recorded outcome even if it is now below the horizon
   (`REQUEST OUTCOME STABILITY` preserved exactly).
2. **Horizon check (new):** if `cmd.StartSeq < f.gcWatermark` →
   deterministic `Outcome{Status: StatusAbortedStale}`, recorded in
   `outcomes` like any other terminal outcome.
3. Conflict check (existing).
4. Apply (existing).

Step 2 is deterministic because `f.gcWatermark` is replicated state and
`cmd.StartSeq` is in the command; every replica reaches the identical
decision. The 1-before-2 ordering is load-bearing and is asserted by
SL-5.

### 15.5 Resolved: no pre-proposal short circuit

`Node.Propose` could reject `StartSeq < localWatermark` before
proposing, saving a Raft round. **Rejected.** It creates a second,
local, potentially-stale decision path for an outcome that is supposed
to be a replicated, recorded, stable fact. One rule, one place: the
outcome is decided in `Apply` and recorded, so `GET /outcome` answers
it forever, exactly like an SI abort. The wasted Raft round is bounded
by admission control, which is the other half of this release.

### 15.6 `StatusAbortedStale` and the decoder hardening it forces

New `fsm.Status` value, `StatusAbortedStale = 3` (after
`StatusCommitted`, `StatusAborted`). It is producible only when
`gcWatermark > 0`, which requires generation 3.

A `v0.5.0` binary's `DecodeState` reads the status byte with no
validation (`status := Status(data[off])`, `internal/fsm/snapshot.go`)
— it would silently accept `3`. That is tolerable only because
`DecodeState` is all-or-nothing and a generation-3 snapshot *always*
carries the generation-3 trailing block, so the same `v0.5.0` decode
fails closed at the trailing-bytes check before the misread outcome is
ever used. The chain is: `StatusAbortedStale` exists ⟹
`gcWatermark > 0` ⟹ generation ≥ 3 ⟹ trailing block present ⟹
`v0.5.0` decode fails. SL-17 asserts every link.

`v0.6.0` nonetheless **hardens the decoder**: `DecodeState` and the
control-outcome decoder reject any status byte outside the known set,
with `ErrMalformedCommand`. This is an independent
`NO SILENT FORMAT MISINTERPRETATION` gap-closure that should land in
this release regardless of GC.

```
const controlKindAdvanceGCWatermark byte = 2   // after controlKindSetClusterVersion = 1

type AdvanceGCWatermarkCommand struct {

```

- Decoding follows `DecodeSetClusterVersion`'s bounded-decoding

  the defense in depth `ControlCommandMarker`'s doc comment already
  describes.

### 16.2 FSM snapshot state: the generation-3 trailing block

Follow `internal/fsm/snapshot.go`'s existing precedent
(`if clusterGeneration >= 2 { membership outcomes }`) exactly:

```
if clusterGeneration >= 3 {
    gcWatermark  uint64
    gcPasses     uint64   // completed full-keyspace walks
    gcPassSeq    uint64   // applied AdvanceGCWatermark commands (§13.4a)
    gcCursorLen  uint32
    gcCursor     [gcCursorLen]byte
}
```

`gcPassSeq` is in the block because the leader's deterministic
`RequestID` is a function of it (§13.4a): a node that caught up by
`InstallSnapshot` must arrive at the same `gcPassSeq` as one that
replayed the log, or the two would disagree about the next
continuation pass's identity. `DecodeState` restores all four fields
and then calls `Store.SetGCWatermark` (§15.2b).

- `fsmStateVersion` stays `1`. `snapshot.FormatVersion` stays `2`.
  **No format-version bump is needed**, because the trailing block is
  additive and generation-gated — the same reasoning
  `docs/enterprise-v1-plan.md` §7 established and `v0.5.0` reused.
- A `v0.5.0` binary decoding a generation-3 snapshot fails closed at
  `"%d trailing bytes after decoding cluster-generation block"`. That
  is the documented rollback boundary, not a bug
  (`ROLLBACK BOUNDARY HONESTY`).
- A generation-2 (or 0) snapshot written by `v0.6.0` is
  **byte-identical** to what `v0.5.0` writes. SL-16 asserts this
  against a committed `v0.5.0`-produced fixture.

### 16.3 WAL and snapshot file formats

Unchanged. No new WAL record type, no new snapshot framing, no change
to `wal.Metadata`, no change to `snapshot.Meta`. The
`AdvanceGCWatermark` command travels as an ordinary
`RecordTypeLogEntry` payload inside an `EntryNormal`, exactly like
`SetClusterVersion`.

## 17. WAL retention and safe segment deletion

### 17.1 The reclamation boundary, named once

> **`ReclaimBoundary`** = the `LastIncludedIndex` of the most recent
> snapshot that is (a) fully written and fsync'd, (b) recorded in
> durable WAL metadata via `AppendMetadataSnapshot`, and (c) whose
> `HardState` has been re-affirmed into the current segment.

Nothing at or below `ReclaimBoundary` is required by any future
recovery of this node. Nothing above it may ever be deleted.

### 17.2 The ordering is preserved step for step (C4)

`maybeSnapshot` (`internal/node/node.go:1814`) performs, in this exact
order, and `v0.6.0` **does not reorder or interleave any of it**:

```
(a) snapMgr.Create(meta, fsm, writeVersion)     // snapshot durable
(b) walog.AppendMetadataSnapshot(lastIncluded)  // pointer durable
(c) core.Compact(lastIncluded)                  // in-memory raft
(d) storage.Compact(lastIncluded)               // in-memory mirror
(e) storage.Reaffirm()                          // HardState into the current segment
(f) walog.CompactBefore(lastIncluded)           // delete whole segments
```

The only `v0.6.0` changes inside this sequence are the pre-emptive
heartbeat before (a) (§4.4), the `event_loop_block_seconds`
observation around it, and the retain-extra parameter on (f) (§17.3).
A test asserts the call order itself, so a future refactor cannot
quietly permute it.

### 17.3 `-wal-retain-extra-segments`

`WAL.CompactBefore(uptoIndex)` gains a sibling
`WAL.CompactBeforeRetaining(uptoIndex, retainExtraSegments int)` (the
existing method becomes `retainExtra = 0`), which stops deleting once
`retainExtraSegments` otherwise-eligible segments remain. Purpose: give
a lagging follower a chance to catch up by log rather than by a full
`InstallSnapshot` — which is, per §4.4, one of the most
event-loop-expensive things a leader can be asked to do.

Safety: retaining **more** history than required is always safe; the
existing eligibility computation ("this segment's highest possible
index is `ids[i+1]-1`") is unchanged — only the stopping point moves
earlier. Default `0` = today's behavior exactly.

### 17.4 What `v0.6.0` explicitly does **not** do to the WAL

- No time-based WAL retention. There is no wall clock in the durable
  layer and this release does not introduce one.
- No partial-segment reclamation.
  [`docs/snapshots.md`](snapshots.md) §8's whole-segments-only rule is
  preserved.
- No deletion of the current (open) segment. Preserved.
- No change to `WAL.Truncate`'s two-phase ordering.

## 18. Snapshot retention and the `InstallSnapshot` interaction

### 18.1 The hazard, precisely

`Manager.writeDurable` calls `pruneExcept(newIndex)` immediately after
a new snapshot is durable. Meanwhile `processOutput`
(`internal/node/node.go:1547`) fills `MsgInstallSnapshotRequest` bytes
from `snapMgr.Bytes(m.LastIncludedIndex)`. Both run on the event-loop
goroutine, so there is no data race — but across two loop iterations a
snapshot can be created (pruning the old file) between Core deciding a
follower needs index `X` and the message being filled. Today that path
logs `"cannot serve snapshot %d to %s … leader will retry"` and drops
the message; Core re-derives a request for the newer index on the next
heartbeat, so it is self-healing. It is, however, **unmeasured and
unbounded in how often it can happen.**

### 18.2 `-snapshot-retain-count`

`Manager` gains `SetRetainCount(n int)` (`n >= 1`); `pruneExcept`
becomes `pruneKeepingNewest(n, keepIndex)`, retaining the newest `n`
snapshot files by index and deleting the rest — still only ever after
the new one is confirmed durable. Default `1` = today's behavior
exactly.

`Manager.Load`'s existing newest-first, fall-back-to-older search
(`candidatesDescending`) already handles `n > 1` with no change; its
doc comment even anticipates it ("or if some future policy retains more
than one generation").

### 18.3 New metric, so the hazard becomes a number

`chronicledb_snapshot_serve_miss_total` increments on the
`ok == false || err != nil` branch in `processOutput`. Gate item
(§31, gate 5): this counter must be **zero** across the real-process
membership + snapshot suite, and a deliberate-miss test (SL-11) must
show it *can* become nonzero — a negative control for the counter
itself.

## 19. Disk-space accounting and the disk-full state machine

### 19.1 States (per node, in-memory, reset on restart)

```
Healthy  --(free < pressureThreshold)------->  LowSpace
LowSpace --(free < criticalThreshold)------->  Critical
Critical --(free >= criticalThreshold*1.1)-->  LowSpace
LowSpace --(free >= pressureThreshold*1.1)-->  Healthy
any      --(fsync/write failure, §20)------->  Failing   [terminal for this process]
```

### 19.2 Behavior per state

| State | Client writes | Client reads | Admin | Raft/consensus | GC |
|---|---|---|---|---|---|
| `Healthy` | full | full | full | full | scheduled |
| `LowSpace` | tightened (§6.4) | full | full | **full, ungated** | triggered immediately |
| `Critical` | rejected, `disk_critical` | full | full | **full, ungated** | triggered immediately |
| `Failing` | node has already halted (§20.1) or is not-ready | — | — | — | — |

### 19.3 Actual `ENOSPC`

Unchanged from `v0.5.0` and from
[`docs/failure-model.md`](failure-model.md) §1.8/§1.9: the write fails
explicitly, no acknowledgment is given, `DURABILITY` holds. `v0.6.0`
adds exactly two things:

1. **Classification.** `internal/wal` and `internal/storage` wrap a
   `syscall.ENOSPC` (detected with `errors.Is`) into
   `wal.ErrOutOfSpace` / `storage.ErrOutOfSpace`, so the caller — and
   `/health`, `/status`, the audit log, and the client-facing error —
   can distinguish "out of space" from "I/O error" from "permission
   denied". This is `DISK-FULL EXPLICITNESS` (§27.9).
2. **Recovery-on-space-freed.** There is no "stuck forever" state for
   `LowSpace`/`Critical`: the next successful poll above the hysteresis
   threshold restores the previous state automatically, with no
   operator action and no restart. SL-15 proves this against a real
   small filesystem.

### 19.4 What pressure never does (C3)

> Disk pressure never deletes anything. It tightens admission and it
> asks GC to run. GC deletes only what `docs/mvcc.md` §6's rule
> permits. There is no code path in `v0.6.0` in which low disk space
> causes any datum a legal reader could still see to be removed.

That paragraph must appear verbatim in `docs/storage-lifecycle.md`.

## 20. fsync-failure handling and node health

### 20.1 The Raft durable path is unchanged

A failure in `raft.ApplyPersistRequest` still calls `Node.fail`, which
halts the node. That is a `v0.5.0` guarantee and `v0.6.0` preserves it
exactly — an fsync failure on the consensus path is not something to
count and tolerate.

What `v0.6.0` adds on that path happens **before** the halt: classify
the error (§19.3), emit the audit record, set `/health` to not-ready,
and increment `chronicledb_fsync_failures_total{path="raft"}` — so the
operator learns *why*, rather than finding a stopped process.

### 20.2 Non-consensus paths get the threshold

Snapshot creation, backup export, and audit-log writes sync outside the
`ApplyPersistRequest` path. These increment a consecutive-failure
counter; on reaching `-fsync-failure-threshold` (default 3) the node
transitions to storage-unhealthy: `/health` not-ready, an audit record,
a log line, and `chronicledb_storage_health = 1`. Any single success
resets the consecutive counter.

The node does **not** self-terminate on storage-unhealthy: it keeps
participating in Raft (voting, replicating) as long as the consensus
path still works, because a node that can still vote is more useful to
the cluster than one that has removed itself. It stops being *ready*,
which is what an operator's automation keys on.

### 20.3 Audit

Every state transition in §19.1 and §20.2 is an audit-log record
(`internal/audit`, hash-chained). These are node-health facts an
operator must be able to reconstruct after the fact, and the audit log
is the one append-only record that already survives independently of
the WAL.

## 21. Storage integrity verification (scrub)

### 21.1 Contract

```
POST /admin/storage/scrub     # admin role only, audited
GET  /admin/storage/status    # operator+, read-only
```

`Node.Scrub(ctx, opts) (ScrubReport, error)`. Report shape:

```
{ "startedAt":…, "durationMs":…, "bytesRead":…,
  "walSegmentsChecked":…, "walFramesChecked":…,
  "snapshotsChecked":…, "auditRecordsChecked":…,
  "findings":[ {"file":"…","offset":1234,"kind":"bad_checksum"} ],
  "truncated": false }
```

`kind` vocabulary (fixed): `bad_checksum`, `bad_framing`,
`unsupported_version`, `index_out_of_order`, `unreadable`,
`snapshot_decode_failed`, `audit_chain_broken`.

### 21.2 Non-destructive, structurally (S-10)

`internal/storage` gains `OpenSegmentReadOnly(dir, id)`, opening with
`os.O_RDONLY` and returning a `*Segment` whose `Append`, `Sync`, and
`Truncate` return `ErrReadOnlySegment`. **Scrub uses only that
constructor**, so `SCRUB NON-DESTRUCTIVE` is a property of the file
descriptor, not of reviewer discipline. Enforced by
`TestScrubOnlyOpensReadOnly` (an AST test, same pattern as CP-2) and by
SL-10's before/after byte-for-byte directory hash comparison.

### 21.3 What it checks, and the one thing it must not flag

- Every WAL segment: framing, per-record checksum, format version,
  `LogEntry` index monotonicity and gap-freedom.
- Every retained snapshot file: `snapshot.Decode` (magic, version
  range, CRC, `LastIncludedIndex`/filename agreement, the
  `hasConfig`/`configLen` cross-check).
- The audit log hash chain.
- **A torn tail in the current (last, open) WAL segment is not a
  finding.** It is legal per [`docs/wal.md`](wal.md) §6. Emitting it as
  corruption would train operators to ignore scrub output. SL-10's
  false-positive control asserts a freshly torn tail produces zero
  findings.

### 21.4 Where it runs

On its own goroutine, **not** the event loop, holding a
`maintenanceGate` slot (Lane A2, never a control slot — Rule CP-3)
plus a dedicated single-slot scrub lock, rate-limited by
`-scrub-bytes-per-sec`. It never takes `FSM.mu` and never touches
`Core`. Consequence: a scrub can run concurrently with normal traffic,
including with a snapshot creation — it reads files the event loop may
concurrently delete, so every `os.IsNotExist` encountered during the
walk is skipped, not reported (a file that was compacted away
mid-scrub was, by definition, not needed).

### 21.5 It never repairs

Consistent with `RECOVERY NON-INVENTION` and
[`docs/recovery.md`](recovery.md) §4: scrub reports, the operator acts.
There is no `?repair=true`, no quarantine move, no truncation.

## 22. Crash safety across every reclamation point

| Crash point | Result | Why safe |
|---|---|---|
| During `snapMgr.Create` | Orphan temp file | `NewManager` removes `tmp/*`; the pointer never advanced |
| After `Create`, before `AppendMetadataSnapshot` | Extra snapshot file | `Load` never trusts a file above the durable pointer (existing behavior) |
| After the pointer, before `CompactBefore` | Extra WAL segments | Recovery replays a little more; the next cycle compacts |
| Mid-`CompactBefore` | Some segments deleted | Each deletion is its own fsync'd directory operation; the remaining set is still a valid prefix (existing behavior, unchanged) |
| Mid-`pruneKeepingNewest` | Extra snapshot files | `Load` is newest-first with fallback; never zero valid snapshots, because prune runs only after the new one is durable |
| **Mid-GC Apply** | The `AdvanceGCWatermark` entry is either committed or not | If committed, WAL replay re-runs `ApplyAdvanceGCWatermark` deterministically and reaches the identical state; if not, nothing happened. **GC has no separate durable bookkeeping of its own** — the watermark and cursor live in FSM state and are reconstructed by replay or restored from a snapshot. |
| Crash between GC Apply and the next snapshot | Reclaimed versions return on replay, are reclaimed again | Idempotent and deterministic |
| During scrub | Nothing | Read-only |
| **During `backup.Export`** | A partial backup directory in `outDir`; **the node's own state is untouched** | `Backup` never mutates this node's retained WAL or snapshot state, never advances the durable snapshot pointer, and never interacts with `maybeSnapshot`'s threshold (`Node.Backup`'s own doc comment). Recovery of the *node* is therefore exactly the crash-free path. The partial *backup* is not recoverable and must not be usable: `backup.Manifest` is written last and carries per-file checksums, so `Restore` fails closed on a missing or short manifest rather than restoring a truncated base |
| **During PITR restore / `-restore-until`** | The in-progress restore target directory | Restore writes into a fresh target directory and is not an in-place mutation of a live node; a crash leaves an incomplete target that the next `Restore` overwrites or that fails its own manifest verification. The *source* backup is read-only throughout |
| **During `handleInstallSnapshot`, before `storage.InstallSnapshot` returns** | The received snapshot file, plus possibly nothing else | `snapMgr.Install` writes through the same temp-file/fsync/rename sequence `Create` uses, and `NewManager` removes `tmp/*` on restart. The durable pointer has not moved, so `Load` never adopts the new file and the node restarts at its previous boundary and re-requests the snapshot |
| **During `handleInstallSnapshot`, after `storage.InstallSnapshot` but before `n.fsmachine.Store(snap.FSM)`** | Nothing committed | The durable pointer now names the new boundary; on restart, recovery loads that snapshot and rebuilds the FSM from it — including `gcWatermark`/`gcCursor`/`gcPassSeq` and the §15.2b `Store.SetGCWatermark` call. The in-memory assignment the crash interrupted is exactly what recovery redoes |
| **During `handleInstallSnapshot`, after the FSM swap, before the generation adopt** | Nothing committed | The adopted generation is durable state recovered from the same snapshot, so restart re-derives it from the installed file rather than from the interrupted in-memory sequence |

The three `handleInstallSnapshot` rows are new in this revision
because §27.8 names `WALStorage.InstallSnapshot` in its scope while
the table did not cover it, and because §15.2b makes snapshot
installation a point at which the *horizon* — not just the data — is
adopted. The required invariant for all three is
`SNAPSHOT SAFETY` + `RECLAMATION BOUNDARY` + the §15.2b equality
`Store.GCWatermark() == FSM.gcWatermark`.

**Proof tiers for the new rows:**

| Rows | Tier | Test |
|---|---|---|
| `backup.Export`, PITR restore | `cmd/chronicledb-node` real process — a crash mid-export is an OS-process fact (partial files, fsync ordering), not something a single-process harness models honestly | **SL-25**: `SIGKILL` during `/admin/backup` and during a PITR restore; assert the node restarts clean with an unchanged data directory hash, and that the partial backup fails `Restore` closed with the manifest error |
| The three `handleInstallSnapshot` rows | `internal/node` `testCluster` with the §33 slice 10a crash-injection hook (real disk, real TCP) | **SL-26**: crash injected at each of the three points during a learner's catch-up; assert the node recovers, converges byte-identically with the rest of the cluster, and satisfies the §15.2b equality at every restart |

The GC row is the strongest property in this table and is a direct
consequence of the §13.2 decision: because reclamation is a pure
function of committed history, **crash safety for GC is the crash
safety the replay machinery already has** — no new mechanism, no new
proof burden. `enterprise-v1-plan.md` §10's "a crash mid-GC leaves some
reclaimable versions unreclaimed" is satisfied a fortiori.

## 23. Interaction with backup, restore, membership, and upgrades

### 23.1 Backup

- `backup.Export` reads the node's adopted snapshot (which carries the
  GC watermark in its generation-3 trailing block) plus, for
  `continuous`, the durable WAL suffix (which may contain
  `AdvanceGCWatermark` entries). Both are already-durable bytes; no
  change to `internal/backup`'s format, manifest, or checksums.
- Backup and snapshot creation cannot interleave — both run on the
  event loop — so `BACKUP CONSISTENCY` holds unchanged.
- **New requirement:** a backup taken from a generation-3 cluster
  records generation 3 in its manifest's existing version fields, and
  restoring it under a `v0.5.0` binary fails closed at `DecodeState`'s
  trailing-bytes check. SL-17 asserts this with a real
  `v0.6.0`-produced backup and a real `v0.5.0` binary (git-worktree
  technique, per `v0.5.0` gate 6's precedent).

### 23.2 Restore

- The restored FSM carries the watermark, cursor and `gcPassSeq` from
  the base snapshot, and `DecodeState` propagates the watermark into
  the restored `mvcc.Store` (§15.2b) so the read guard is live from
  the first read, not from the next `AdvanceGCWatermark`. **A restore
  never lowers the watermark** — the point of the monotone `max()` in
  §14.4 step 1 — and never resurrects a reclaimed version (they are
  not in the backup).
- PITR (`-restore-until=N`) restores to a committed index `N` at or
  above the base snapshot's index. Reads after restore use
  `StartSeq >= restored applied index >= watermark`, so the horizon
  guard never fires spuriously on a restored node. SL-18.
- `RESTORE MEMBERSHIP ISOLATION` is untouched: GC state is FSM state
  and is restored exactly, unlike membership, which is deliberately
  re-bootstrapped.

### 23.3 Membership and `InstallSnapshot`

- A snapshot installed by a follower carries the sender's watermark,
  cursor and `gcPassSeq`, and the receiver adopts them wholesale via
  `DecodeState` — which is correct, because the sender's watermark was
  itself established by committed history the receiver is adopting.
  `DecodeState`'s `Store.SetGCWatermark` call (§15.2b) is what keeps
  the receiver's read guard consistent with the state it just
  adopted; without it, `handleInstallSnapshot`'s wholesale FSM swap
  (`internal/node/node.go:2011`) would leave the guard at 0.
- A **learner** catching up either replays log entries (applying
  `AdvanceGCWatermark` deterministically) or installs a snapshot
  (adopting the watermark). Either way it converges to the identical
  state. SL-13.
- Learners do not serve reads, so a catching-up learner contributes no
  lease and can never hold the watermark back.

### 23.4 Upgrades

Generation 3 gates everything (§24). The
`MEMBERSHIP CHANGE GENERATION GATE` precedent applies directly: **no
`AdvanceGCWatermark` may be proposed or applied below generation 3**,
enforced on both sides (the leader refuses to propose;
`applyControlEntry` fails closed on receipt). The two-sided gate is not
optional — `v0.5.0`'s §8.2 review established that a one-sided gate is
insufficient.

## 24. Compatibility: `v0.5.0` → `v0.6.0`

### 24.1 Generation 3, defined

Add to `internal/version`:

```
// Generation 3 (v0.6.0, docs/v0.6.0-plan.md §24) is defined as: this
// binary understands the AdvanceGCWatermark FSM control command
// (control kind 2), the fsm.StatusAbortedStale outcome status, and the
// generation-3 snapshot-state trailing block carrying gcWatermark,
// gcPasses, gcPassSeq, and gcCursor. No GC watermark advance may be
// proposed or applied below this generation.
const MaxSupportedGeneration uint32 = 3
```

`docs/upgrades.md` gains §8b mirroring §8a's structure.

### 24.2 The compatibility matrix

| Scenario | Outcome | Mechanism |
|---|---|---|
| `v0.5.0` and `v0.6.0` nodes in one cluster, generation 2 | Works. No GC possible (leader-side gate refuses). | Generation gate |
| Mixed cluster, operator calls finalize to 3 | Refused unless **every** member reports `MaxSupportedGeneration >= 3` | Existing `UpgradePrecheck` |
| Generation 3, a `v0.5.0` node rejoins | Fails closed on the first generation-3 snapshot or control entry it sees | `NO SILENT FORMAT MISINTERPRETATION` |
| `v0.6.0` reads a `v0.5.0` snapshot (generation 0/1/2) | Works | `MinReadVersion`, trailing-block gating |
| `v0.6.0` writes at generation ≤ 2 | Byte-identical to `v0.5.0` output | SL-16 |
| `v0.6.0` restores a `v0.5.0` backup | Works | Existing restore path, unchanged |
| `v0.5.0` restores a generation-3 backup | Fails closed | SL-17 |
| Downgrade `v0.6.0` → `v0.5.0` at generation ≤ 2 | Supported | `ROLLBACK BOUNDARY HONESTY` |
| Downgrade after finalizing to 3 | **Not supported.** The documented rollback boundary. | Same |

### 24.3 Client-facing compatibility (additive, MINOR)

Three additive changes existing clients must be documented to handle:

1. `503` + `Retry-After` is now a possible response to `/propose` and
   every `/admin/*` endpoint. Previously impossible.
2. `status: "ABORTED_STALE"` is a new value in the `/propose` and
   `/outcome` response `status` field. Previously impossible, and
   still impossible unless GC is enabled.
3. HTTP timeouts and connection caps are now enforced (§10.4).

Per [`docs/versioning.md`](versioning.md) all three are
MINOR-compatible additions, and all three go in `CHANGELOG.md` under an
explicit "Behavior changes" heading, not buried in a feature list.

### 24.4 The `v1.0.0` gate items this release creates

`enterprise-v1-plan.md` §17.1 item 3 requires MVCC GC to run **by
default** at `v1.0.0`, proven by a long-duration run. `v0.6.0` ships it
**disabled** (`-gc-interval=0`). §31 gate 13 requires that deferral to
be recorded in `docs/roadmap.md` and `docs/storage-lifecycle.md` so it
is not lost between releases.

### 24.4a The `v1.0.0` blocker `v0.6.0` must not let disappear

`enterprise-v1-plan.md` §17.1 item 3 does not stop at "GC runs by
default". Its full text requires:

> …with a real long-duration (§15) run proving **stable disk usage**
> under continuous load with GC enabled by default.

`v0.6.0` is correct to leave the `RequestID` outcome table alone
(§28.2, deviation D6) — pruning it would directly weaken
`IDEMPOTENCY` and `REQUEST OUTCOME STABILITY`, which this release is
forbidden to touch — and correct to scope SL-19 to MVCC version count
over a bounded key set rather than to total disk usage. Nothing in
this release overclaims.

What must not happen is that the *forward* obligation evaporates.
With an unbounded outcome table, §17.1 item 3 as worded is
**unsatisfiable**, so exactly one of two things has to happen before
`v1.0.0` is tagged:

1. `RequestID` outcome-table retention lands (a bounded window, or a
   `RequestID`-expiry contract negotiated with clients), with its own
   ADR, because it touches `IDEMPOTENCY`; **or**
2. `enterprise-v1-plan.md` §17.1 item 3's "stable disk usage" wording
   is formally rescoped — by the maintainer preparing `v1.0.0`, in
   that document, with the same evidence discipline §17.4 requires —
   to the claim the system can actually support.

Filing this only in `docs/non-goals.md`, as an earlier draft did,
would be the accidental-forever deferral: `non-goals.md` is where
things go *not* to be done, and it names no owner release. §31
gate 13 therefore requires this item to be recorded in
`docs/roadmap.md` as a **`v1.0.0` blocker with a named owner gate**
(`enterprise-v1-plan.md` §17.1 item 3), alongside the two deferrals
above, and `docs/storage-lifecycle.md` must carry the same statement
where it documents the table's unbounded growth.

`v0.6.0` does **not** solve `RequestID` retention, and this section
authorizes no work on it.

# PART C — CORRECTNESS

## 27. Invariants

Each is written in [`docs/invariants.md`](invariants.md)'s existing
six-part format (statement, scope, why it matters, mechanism,
threatened by, proof/test obligations) and must be added to that
catalog — not a shadow catalog — when implemented. Ten new, one
amended, two annotated.

### 27.1 `BOUNDED ADMITTED WORK`

- **Statement**: The number of client proposals concurrently
  proposed-but-unapplied on a node never exceeds
  `-max-inflight-proposals`; the number of pending `ReadIndex`
  requests never exceeds `-max-concurrent-reads`; the number of live
  read leases never exceeds `-max-live-read-leases`; and the number of
  goroutines concurrently inside any admission gate never exceeds that
  gate's `MaxConcurrent + MaxQueueDepth`.
- **Scope**: Every node, every moment, replicated mode.
- **Why it matters**: An unbounded admitted set is an unbounded memory
  commitment and an unbounded event-loop backlog — the failure mode
  that turns a slow cluster into a dead one.
- **Mechanism**: Fixed-capacity channels in `admission.Gate` (§5.2)
  bound *goroutines and resident payload memory*. Three independent
  event-loop ceilings — `len(n.waiters)` (§5.3),
  `len(n.pendingReads)` and the live-lease count (§9.1a) — bound the
  per-node state a request leaves behind.
  **These are not interchangeable.** The gate does **not** bound
  `waiters` or `pendingReads`, because a caller that cancels its
  context frees its gate slot while its waiter and pending read
  survive (facts 8c, 8d). The event-loop ceilings are the
  authoritative mechanism for this invariant; the gates are the
  authoritative mechanism for the memory bound in §5.2.
- **Threatened by**: A new client entry point added without a gate; a
  gate constructed with `MaxConcurrent <= 0`; a `release` that is not
  deferred; a new piece of per-request node state introduced without
  its own event-loop ceiling.
- **Proof/test obligations**: AC-1 (exact boundary), AC-2 (`-race`,
  1000 iterations), AC-3 (`len(waiters)` never exceeds the bound across
  a full chaos schedule), AC-14 (defense counter stays 0 in the tests
  with no client cancellation), **AC-20** (cancel-heavy workload: the
  defense counter *does* fire and the ceiling still holds),
  **AC-21** (`pendingReads` and lease ceilings hold under a
  never-resolving minority-partition read flood; `minLease` is
  `O(1)`), AC-18 (structural AST test).

### 27.2 `CONTROL-PLANE NON-STARVATION`

- **Statement**: The latency of processing one inbound Raft message,
  and of dispatching one heartbeat round, is not a function of client
  admission-queue depth, client request concurrency, or client
  rejection rate. **This invariant does not claim the event loop is
  never blocked**: snapshot creation, backup export, and snapshot
  installation still run to completion on it (§4.4), bounded and
  measured but not eliminated.
- **Scope**: `internal/node`'s event loop, replicated mode.
- **Why it matters**: `RAFT ELECTION SAFETY` is a safety property, but
  Raft's *availability* depends on timely heartbeat processing;
  starving it because of client load turns an overload into an
  election storm.
- **Mechanism**: Lane separation with no shared structure (§3.2,
  §3.2a); no admission identifier reachable from `run()` (§4.2). Plus
  the three fixes §4.3 enumerates, each of which would otherwise make
  the statement false: `FSM.mu` as an `RWMutex` (§5.4a), the
  `pendingReads` ceiling that bounds `checkPendingReads`'s
  per-message scan (§9.1a), and `MaxKeys`-bounded GC Apply (§14.4).
- **Threatened by**: Anyone adding a gate acquisition inside the event
  loop "for symmetry"; sharing one gate between Lane A and Lane B, or
  merging Lane A1 and Lane A2 back together; adding an ungated
  endpoint that takes `FSM.mu` in exclusive mode; adding per-message
  loop work proportional to an unbounded set.
- **Proof/test obligations**: AC-6 (`internal/node` `testCluster`, per
  §29.3 — saturated client gate vs. heartbeat latency), AC-10 (real
  cluster, zero elections under sustained saturation), **AC-19**
  (ungated `/outcome` + `/status` flood vs. Raft message-processing
  p99), **AC-21** (`checkPendingReads` cost bounded), **AC-22**
  (concurrent backup + scrub does not delay a membership change),
  **SL-2b** (GC Apply cost flat in total key count), AC-18 (AST,
  covering Rule CP-2 and Rule CP-3), plus the negative controls AC-7
  (lane separation disabled by a test hook → the same scenario *does*
  produce elections) and AC-19's exclusive-mutex control.

### 27.3 `REJECTION SAFETY`

- **Statement**: A request rejected for capacity has never been
  proposed, replicated, or applied; no `RequestID` was recorded; the
  rejection is always safe to retry and never produces a duplicate
  effect.
- **Scope**: Every admission rejection, every lane.
- **Why it matters**: Extends `IDEMPOTENCY` to the new rejection path
  explicitly. A rejection that *might* have partially happened is worse
  than no rejection at all.
- **Mechanism**: Every gate acquisition strictly precedes the channel
  send into the event loop, and therefore precedes
  `Core.Step(InputPropose)` (§8.4).
- **Threatened by**: Moving a gate after the propose; recording a
  metric keyed by `RequestID` on the rejection path.
- **Proof/test obligations**: AC-8 (50%-rejection stress with recycled
  `RequestID`s, checked by `internal/oracle` for zero duplicate effects
  and zero `RequestID`s with two outcomes), AC-9 (a rejected request's
  `RequestID` is `ErrRequestIDUnknown` at `/outcome`).

### 27.4 `ADMISSION FAILS CLOSED`

- **Statement**: Any failure, misconfiguration, or absence of the
  admission mechanism results in *rejecting* work, never in admitting
  unbounded work.
- **Scope**: Configuration parsing, gate construction, and every
  request path.
- **Why it matters**: An availability cost is preferred over resource
  exhaustion — the same posture `AUDIT COMPLETENESS` already takes for
  the audit log.
- **Mechanism**: `MaxConcurrent <= 0` is a startup error; there is no
  "unlimited" value; the event-loop ceiling rejects independently;
  `Acquire` never returns a nil error without a held slot.
- **Threatened by**: Adding a `-disable-admission` flag; treating a
  gate-construction error as a warning.
- **Proof/test obligations**: AC-4 (each invalid configuration refuses
  startup with a specific message), AC-5 (a deliberately no-op gate
  injected via a test hook still cannot exceed the bound, because the
  event-loop ceiling holds).

### 27.5 `GC SAFETY`

- **Statement**: A version is removed only when `docs/mvcc.md` §6's
  rule permits it, and no transaction ever *observes* a version GC has
  removed: any read or commit whose `StartSeq` is below the applied GC
  watermark is refused, never silently served from the surviving chain.
- **Scope**: `internal/mvcc`, `internal/fsm`, every replica, all time.
- **Why it matters**: Reclaiming a version a live snapshot still needs
  is the canonical MVCC-GC correctness bug, and — worse than an error —
  it manifests as a *silent* Snapshot Isolation violation (§15.1).
- **Mechanism**: §14.1's predicate applied inside `fsm.Apply` against
  the post-`max()` `f.gcWatermark` (§14.4, the single authoritative
  horizon); §15.2's horizon guard inside `mvcc.Store` under the same
  lock as the chain read, reached by **every** committed-read path
  including prefix scans (§15.2a); the §15.2b equality
  `Store.GCWatermark() == FSM.gcWatermark` after restore, install and
  restart; §15.4's deterministic commit-side abort.
- **Threatened by**: A read path reaching `chains` without going
  through `Visible`/`ScanVisible` — `Store.Export` is the one that
  historically did, which is why §15.2a restricts it to snapshot
  encoding and asserts that structurally; a restored `Store` left at
  watermark 0; lowering the watermark; computing the watermark from
  anything but committed state; reclaiming against `cmd.Watermark`
  rather than `f.gcWatermark`.
- **Proof/test obligations**: SL-1 (property test: randomized chains ×
  randomized snapshot sets × randomized watermarks, at the existing
  MVCC property-test seed discipline, asserting no surviving snapshot's
  required version was removed and every removed-version read is
  refused), SL-2 (the same property under the deterministic chaos
  schedule with GC active), SL-3 (negative control: with the horizon
  guard disabled by a test hook, the property test **detects** the
  silent stale read).

### 27.6 `GC DETERMINISM`

- **Statement**: The set of versions reclaimed by a node, and its
  resulting GC cursor and watermark, are a pure function of the
  committed log prefix that node has applied — identical on every
  replica, and identical across replay, restart, and snapshot restore.
- **Scope**: `internal/fsm.ApplyAdvanceGCWatermark`, `internal/mvcc`.
- **Why it matters**: It is what keeps `STATE MACHINE SAFETY` and
  `DETERMINISM BOUNDARY` true after GC exists (§13.1).
- **Mechanism**: Reclamation only inside `Apply`; explicitly sorted key
  iteration via `Store.KeysFrom`; **both** `MaxVersions` and `MaxKeys`
  carried in the command rather than read from local config; the
  post-`max()` `f.gcWatermark` as the single comparison horizon
  (§14.4); monotone `max()` on the watermark; `gcPassSeq` advanced in
  `Apply` so the leader's next `RequestID` is itself a function of
  replicated state (§13.4a).
- **Threatened by**: A background goroutine mutating `Store`; map
  iteration order; reading `-gc-max-versions-per-pass` or
  `-gc-max-keys-per-pass` inside `Apply`; a per-node "skip GC when
  busy" heuristic; deriving the GC `RequestID` from anything a
  replica cannot recompute from its own applied state.
- **Proof/test obligations**: SL-4 (two independently constructed FSMs
  fed the identical history including GC commands produce
  byte-identical `EncodeState`), **SL-4a** (a command whose
  `Watermark` is below `f.gcWatermark` reclaims against the current
  watermark, not the command's), **SL-2b** (Apply cost flat as total
  key count grows 10×), SL-12 (chaos: every live node's `EncodeState`
  at the same applied index is byte-identical, with GC active), SL-13
  (a node that caught up by `InstallSnapshot` and one that caught up
  by log replay agree byte for byte, including `gcPassSeq` and the
  §15.2b equality).

### 27.7 `SNAPSHOT HORIZON ENFORCEMENT`

- **Statement**: Every read of committed MVCC state, and every commit
  decision, is refused if its `StartSeq` is below the applied GC
  watermark — structurally, at the `internal/mvcc` boundary, with no
  bypass.
- **Scope**: `internal/mvcc.Store` (all read entry points),
  `internal/fsm.Apply`.
- **Why it matters**: It is the mechanism that makes `GC SAFETY`
  unconditional rather than "sound as long as the leader knew about
  every reader."
- **Mechanism**: `Visible`/`ScanVisible` return `ErrSnapshotTooOld`;
  `Apply` returns `StatusAbortedStale`; both read the watermark under
  the same lock as the data. `Store.Export` is restricted to snapshot
  encoding (§15.2a) and `internal/sql`'s duplicate visibility helper
  is deleted, so there is exactly one implementation of the rule.
  `DecodeState` propagates the watermark into the restored `Store`
  (§15.2b), so the guard is live on a restored or snapshot-installed
  node from its first read.
- **Threatened by**: A new read accessor added to `Store` without the
  check; a caller re-deriving visibility from `Export` outside
  `internal/mvcc`; exposing `chains` directly; a restored `Store`
  constructed without a watermark.
- **Proof/test obligations**: SL-5 (ordering: idempotency before
  horizon before conflict), **SL-6** (every committed-read *entry
  point the product actually has* — `replicatedTxn.Get`/`ScanPrefix`,
  `standaloneTxn.Get`/`ScanPrefix`, and every exported `mvcc.Store`
  read method — refuses below the horizon; scoped to paths, not to
  `Store`'s method set, because a method-set test passes on an unused
  `ScanVisible`), **SL-6a** (`Store.GCWatermark() == FSM.gcWatermark`
  as a `DecodeState` post-condition over the SL-1 corpus),
  **SL-6b** (`TestExportOnlyCalledFromSnapshotEncoding`, AST), SL-7
  (a stale transaction's commit aborts identically on every replica
  and is recorded stably).

### 27.8 `RECLAMATION BOUNDARY`

- **Statement**: No durable WAL segment or snapshot file is deleted
  before the snapshot that supersedes it is fully written, fsync'd,
  recorded in durable WAL metadata, and has had `HardState`
  re-affirmed; and nothing above that boundary is ever deleted.
- **Scope**: `internal/wal.CompactBefore*`,
  `internal/snapshot.Manager.pruneKeepingNewest`,
  `WALStorage.InstallSnapshot`.
- **Why it matters**: This is `LOG COMPACTION SAFETY` restated at the
  exact ordering level, made explicit because `v0.6.0` introduces new
  retention knobs touching the same code.
- **Mechanism**: §17.2's unchanged six-step ordering (asserted by a
  call-order test); prune-after-durable in `writeDurable`;
  whole-segments-only; never the current segment.
- **Threatened by**: An "optimization" that compacts before the pointer
  write; a retain count of 0; partial-segment reclamation.
- **Proof/test obligations**: SL-8 (crash injection at each of the six
  ordering points, restart, assert recoverable and no committed entry
  lost — at the `internal/node` `testCluster` tier using the **new**
  crash-injection facility of §33 slice 10a, *not* `internal/fault`,
  which has no snapshot manager, no `internal/wal` and no
  `internal/storage`; see §29.3 and deviation D10), **SL-26** (crash
  at each of the three `handleInstallSnapshot` points, §22), SL-9
  (`-snapshot-retain-count=0` refuses startup).

### 27.9 `DISK-FULL EXPLICITNESS`

- **Statement**: An out-of-space condition is always surfaced as an
  explicit, distinguishable failure — never conflated with a
  transaction conflict, a generic I/O error, or an admission rejection
  — and never silently treated as success.
- **Scope**: `internal/wal`, `internal/storage`, `internal/node`, the
  HTTP surface.
- **Why it matters**: A client that cannot distinguish "the cluster is
  full" from "you lost a conflict" will retry the wrong thing forever.
- **Mechanism**: `errors.Is(err, syscall.ENOSPC)` classification into
  `wal.ErrOutOfSpace`/`storage.ErrOutOfSpace` (§19.3); the distinct
  `disk_critical` admission reason (§8.2); distinct `/health` and
  `/status` fields.
- **Threatened by**: Wrapping an `ENOSPC` into a generic
  `fmt.Errorf("write failed: %w")` that loses the classification at a
  package boundary.
- **Proof/test obligations**: SL-14 (real small filesystem, real
  `ENOSPC`: the classified error reaches the client and `/health`),
  SL-14b (`ENOSPC` is never reported as an SI abort), SL-15 (recovery
  after space is freed, with no restart).

### 27.10 `SCRUB NON-DESTRUCTIVE`

- **Statement**: The integrity-verification scrub never modifies
  on-disk state; running it against a live node is always safe.
- **Scope**: `internal/node.Scrub` and everything it calls.
- **Why it matters**: A verification tool that can damage what it
  verifies will not be run when it is most needed.
- **Mechanism**: `storage.OpenSegmentReadOnly` (`O_RDONLY`;
  `Append`/`Sync`/`Truncate` return `ErrReadOnlySegment`); no `FSM.mu`,
  no `Core` access.
- **Threatened by**: A future "scrub can also fix the torn tail" idea.
- **Proof/test obligations**: SL-10 (directory hashed before and after
  a scrub over corrupted and clean data — byte-identical), plus
  `TestScrubOnlyOpensReadOnly` (AST).

### 27.11 `NO SILENT FORMAT MISINTERPRETATION` (extended by `v0.6.0`)

Amended in place, never re-added. The `v0.6.0` extension: control-kind
byte `2` (`AdvanceGCWatermark`), outcome status byte `3`
(`StatusAbortedStale`), and the generation-3 snapshot trailing block
are each rejected — never guessed at — by any binary that does not
understand them; and `v0.6.0`'s own `DecodeState` newly rejects any
unrecognized status byte, closing a gap in the `v0.5.0` decoder
(§15.6).

### 27.12 Invariants explicitly *not* weakened

Asserted here so the release gate can check it: `DURABILITY`,
`ATOMICITY`, `ABORT SAFETY`, `RECOVERY NON-INVENTION`,
`MVCC VISIBILITY`, `CONFLICT CORRECTNESS`, `IDEMPOTENCY`,
`REQUEST OUTCOME STABILITY`, `RAFT ELECTION SAFETY`,
`RAFT LOG MATCHING`, `LEADER COMPLETENESS`, `STATE MACHINE SAFETY`,
`QUORUM SAFETY`, `APPLIED-PREFIX SAFETY`, `SNAPSHOT SAFETY`,
`LOG COMPACTION SAFETY`, `ISOLATION TRUTHFULNESS`,
`CONSISTENT LOG RESPONSIBILITY`, `DETERMINISM BOUNDARY`, and every
`v0.2.0`-`v0.5.0` invariant hold unchanged. Two need a word:

- **`MVCC VISIBILITY`** is *narrowed in domain, not weakened*: it now
  applies to snapshots at or above the GC horizon, and below the
  horizon the answer is an explicit error rather than a value. A
  refused read is not a wrong read. `docs/invariants.md`'s
  `MVCC VISIBILITY` entry gains one sentence saying exactly this, and
  `docs/mvcc.md` §3 gains the same sentence.
- **`ISOLATION TRUTHFULNESS`** is *strengthened*: §15.1's analysis is
  precisely a case where a naive GC would have made the system quietly
  less isolated than it claims, and the horizon guard forbids it.

### 28.1 Failure-semantics table (to be merged into `docs/failure-model.md`)

| Condition | May be lost | Must survive | Must never happen | Client sees |
|---|---|---|---|---|

### 28.2 Two honest limits this release does not fix

1. **The `RequestID` outcome table grows without bound.**
   `fsm.outcomes` gains one entry per distinct `RequestID`, forever, in
   RAM and in every snapshot. GC does not touch it, and `v0.6.0`
   deliberately does not prune it: pruning would directly weaken
   `IDEMPOTENCY` and `REQUEST OUTCOME STABILITY`, which are `v0.5.0`
   guarantees this release is forbidden to weaken. Therefore:
   - `chronicledb_requestid_outcomes` is exported so the growth is
     visible (§25);
   - `docs/storage-lifecycle.md` states plainly that a workload with a
     unique `RequestID` per request has unbounded state growth
     regardless of GC;
   - SL-19's long-running test asserts **MVCC version count**
     stabilizes over a bounded key set — the claim GC can actually
     support — rather than "total disk usage stabilizes", which it
     cannot (deviation D6);
   - outcome-table retention (a bounded window, or a `RequestID`-expiry
     contract negotiated with clients) is named as requiring its own
     ADR and its own release;
   - and — the part an earlier draft left only in
     `docs/non-goals.md` — **it is recorded as a `v1.0.0` blocker
     with a named owner gate** (§24.4a): before `v1.0.0` is tagged,
     either retention lands or `enterprise-v1-plan.md` §17.1 item 3's
     "stable disk usage" wording is formally rescoped. Gate 13
     requires that entry in `docs/roadmap.md`, not only in
     `docs/non-goals.md`, because a non-goal names no owner release
     and is how a requirement gets deferred forever.

   `v0.6.0` solves none of this, and claims no globally bounded disk
   or memory anywhere in its shipped documentation (gate 14).

2. **The final tombstone of a deleted key is never reclaimed** (§14.3).
   Reclaiming it needs a "key is fully absent" notion `docs/mvcc.md` §7
   does not have. Deferred, documented, measured via
   `chronicledb_mvcc_keys`.

# PART D — PROOF / TESTING

## 29. Testing principles applied

Three disciplines this repository already established, applied to every
new gate in this release:

1. **Negative controls**
   ([`docs/testing-strategy.md`](testing-strategy.md) §11). Every
   safety gate here ships with a test-only disable hook and a test
   asserting the harness's oracle *detects* the resulting violation, in
   the same change as the gate's positive test. Hooks:
   `mvcc.SetSkipHorizonGuardForTest`,
   `node.SetSkipAdmissionLaneSeparationForTest`,
   `node.SetNoopAdmissionGateForTest`,
   `fsm.SetExclusiveOutcomeLockForTest` (AC-19's control, §5.4a — with
   `fsm.ArmReadRendezvousForTest`, §30.1a's oracle for observing what it
   does to a *real process*), and `fsm.SetFullSortGCWalkForTest`
   (SL-2b's control, §14.4).
2. **No sleep-based proofs** (C2). Deterministic tests use
   `internal/fault`'s logical tick where the harness reaches (pure
   `raft.Core` scenarios), the `internal/node` hooks §29.3 names
   where it does not, and injected `PressureSource`s for every
   resource test; real-cluster tests poll a *condition* with a
   generous deadline, and
   — per this repository's own experience with fsync-heavy operations
   — those deadlines are sized for synchronous-fsync cost, not for a
   fast machine.
3. **Proof-tier substitution is declared**
   ([`docs/testing-strategy.md`](testing-strategy.md) §12). Where a
   scenario cannot be exercised at the tier this plan names, the
   substitution and its reason are written down, not silently made.
   §29.3 does that for every case in this release.

### 29.3 The `internal/fault` limitation, and every substitution it forces

`internal/fault` imports **exactly one** ChronicleDB package:
`internal/raft`. Verified across every file in it. It therefore
contains no `internal/fsm`, no `internal/node` and no event loop, no
`internal/wal`, no `internal/snapshot` and no `internal/storage`; its
`MemoryStorage` is an in-memory `raft.Storage` whose only injectors
are `FailNextAppends`, `FailNextSetHardState` and `FailNextTruncate`.

An earlier draft declared this for GC alone and then asserted that no
unresolved item remained. The same limitation invalidates **four**
named tiers in this plan, and `enterprise-v1-plan.md` §9 and §10 both
name `internal/fault` explicitly, so this is deviation D10, not a
silent retier:

| Test | Why `internal/fault` cannot run it | Substituted tier | What replaces the deterministic driver |
|---|---|---|---|
| **AC-6** (`CONTROL-PLANE NON-STARVATION`, positive) | Admission gates and the event loop are in `internal/node`; `internal/fault` has neither | `internal/node` `testCluster` (real disk, real TCP, one process) | The existing election-clock freeze (`PauseTicksForTest`/`ResumeTicksForTest`, which never freezes heartbeats) plus an explicit forced-heartbeat driver, with the comparison made on `chronicledb_raft_message_process_seconds` bucket counts rather than wall-clock sleeps (C2) |
| **AC-7** (the negative control for AC-6) | Same | Same | Same, with `node.SetSkipAdmissionLaneSeparationForTest` |
| **SL-2 / SL-12** (GC property + chaos) | GC lives in `internal/fsm`; the harness has no FSM | SL-2 stays a pure `internal/fsm` property test; SL-12 runs at `internal/node` `testCluster` | The existing deterministic action schedule at `CHRONICLEDB_CHAOS_SEEDS` discipline |
| **SL-8** (`RECLAMATION BOUNDARY` crash injection) | §17.2's six steps are `snapMgr.Create`, `AppendMetadataSnapshot`, `core.Compact`, `storage.Compact`, `Reaffirm`, `CompactBefore` — none of which exist in a `raft.Storage` fake | `internal/node` `testCluster` with a **new** crash-injection facility (§33 slice 10a) | A deterministic injection point per ordering step, selected by index, not by timing |

**The facility SL-8 and SL-26 need does not exist and must be

### 30.1a AC-19's negative control: why the oracle is reader overlap

AC-19's positive test is worded in §30.1 against
`raft_message_process_seconds` p99, and that is the right assertion for
the positive case: it is the invariant `CONTROL-PLANE NON-STARVATION`
(§27.2) states, measured where §4.3 says it must hold. The **negative
control** is a different question — "would this test have failed if the
mechanism were removed?" — and the same metric turns out to be
structurally unable to answer it.

**Why a latency oracle cannot discriminate.** `GetOutcome`'s critical
section is one map lookup: tens of nanoseconds. Serializing it behind an
exclusive mutex therefore adds, across even hundreds of concurrent
callers, microseconds of aggregate queuing delay. Both candidate latency
oracles — `raft_message_process_seconds` p99, where the signal is
additionally diluted by heartbeat/`AppendEntries` traffic that never
touches `FSM.mu` at all, and client-observed `/outcome` round-trip p99,
where it is not — measure in milliseconds, against a scheduling and
network noise floor three or more orders of magnitude larger than the
effect. This was confirmed empirically at several concurrency levels
with `-debug-force-exclusive-outcome-lock` set, in one run the
"regressed" case measuring *lower* than the baseline. That is not a
property of the host and more load does not fix it: it is a property of
a nanosecond-scale critical section. A threshold tuned until this
"passed" would be passing on noise.

**What §5.4a actually claims.** Not that `/outcome` is fast — that it
takes `FSM.mu` in *shared* mode, so the number of client lookups
simultaneously inside that critical section is unbounded rather than
exactly one. That is a **counting** property. It discriminates by a
factor of N rather than by noise; it is exact rather than statistical;
and it is *infinitely* sensitive, because under a true mutex an overlap
of two is not unlikely, it is impossible.

**The mechanism.** `internal/fsm/readrendezvous.go` adds a one-shot
rendezvous barrier, armed only by a test and entered only from inside
`GetOutcome`'s critical section, under whichever lock mode `rLock`
chose. It reports how many readers were inside at once (`Peak`), how
many arrived at all (`Arrived`), and whether the barrier filled
(`Reached`). `cmd/chronicledb-node`'s `/fault` endpoint — already the
approved, off-by-default real-process fault surface (§5 layer 8 of
`docs/enterprise-v1-plan.md`, registered only under
`-enable-fault-endpoint`) — gains two node-scoped actions to arm it and
read the result, which is what makes it reachable against a genuine OS
process. Unarmed, which is always the case in production, the whole
mechanism is one atomic pointer load per `GetOutcome`.

**The result**, from two real three-node clusters, one of them started
with `-debug-force-exclusive-outcome-lock`, with 8 concurrent `/outcome`
requests on 8 distinct connections:

| Mode | `Arrived` | `Peak` | `Reached` |
|---|---|---|---|
| shared (production `RWMutex`) | 8 | **8** | true |
| exclusive (injected regression) | 8 | **1** | false |

Identical arrivals — so the control cannot be explained by "the requests
were never sent" — and a categorical difference in overlap. No sleep, no
retry, no load, and no assertion anywhere on elapsed time: the positive
case resolves the instant the eighth reader arrives, and the barrier's
deadline exists only as the negative case's bounded detection bound.

**Why this is not a weakened gate.** §31 gate 3 requires that a real
regression be *detected* at the real-process tier. It is — categorically
rather than statistically, and it now proves something the unit-tier
control (`internal/fsm/rwlock_test.go`'s
`TestExclusiveOutcomeLockForTestSerializesReads`) cannot: that client
concurrency arriving at the shipped binary's HTTP boundary survives as
concurrency all the way into `FSM.mu`'s critical section. What changed
is the *oracle*, from one that provably cannot fail when the mechanism
is removed to one that provably must. The scenario, the tier and the
claim are unchanged.

**Scope.** The overlap measurement is taken with the FSM write path
quiet (`-gc-interval=0`, no proposals in flight). That is deliberate and
is the same property under test seen from the other side: Go's
`RWMutex` blocks new readers once a writer is waiting, which is exactly
why a stream of `/outcome` calls cannot starve the event loop's `Apply`
(§5.4a). AC-19's sustained-Raft-traffic scenario is the positive test's
job; this one isolates the lock mode.

### 30.3 Real-process suite (`cmd/chronicledb-node`)

One end-to-end suite, on real OS processes, real TCP, real disk,
mirroring `v0.5.0`'s §16 precedent:

1. Three real nodes; sustained `/propose` load at 4× the configured
   admission limit, from multiple clients.
2. Assert: the steady-state `503` rate matches the excess; every
   admitted request completes; RSS is bounded; **zero elections**;
   `/health`, `/status`, `/metrics`, and `/outcome` answer throughout.
3. Concurrently: a membership add + promote + remove, an
   `/admin/upgrade/precheck`, an `/admin/backup`, and an
   `/admin/storage/scrub` — every one succeeds while clients are being
   shed. The backup and the scrub must be **overlapping and still
   running** when the membership calls are issued, so Lane A2
   saturation is actually exercised against Lane A1 (§3.2a); a
   sequential arrangement would pass without proving anything.
3a. A concurrent `/outcome` flood at the connection cap, sustained
   through steps 1-3, with `raft_message_process_seconds` p99 held
   within the step-0 baseline (§5.4a).
4. Finalize to generation 3; enable GC; run load over a bounded key
   set; assert `mvcc_versions` stabilizes and `gc_watermark` advances,
   that `gc_passes_total` advances (proving continuation passes work,
   §13.4a), and that `mvcc_gc_apply_seconds` does not grow as the key
   set grows (§14.4).
5. Fill the filesystem to `Critical`; assert writes are refused with
   `disk_critical` while reads and admin succeed; free space; assert
   automatic recovery.
6. `SIGKILL` the leader mid-load; assert failover, no token leak, no

7. Restart every node; assert admission state resets, the GC
   watermark, cursor and `gcPassSeq` survive, that
   `Store.GCWatermark() == FSM.gcWatermark` on every restarted node
   before its first read (§15.2b), and that the scenario corpus
   passes.
8. Report `chronicledb_requestid_outcomes` at the start and end of
   the run, as a measured number, alongside the explicit statement
   that `v0.6.0` makes **no** globally-bounded-disk claim (§28.2,
   gate 14).

### 35.1 Unresolved items for the implementing session

**No unresolved safety decision remains**, and — unlike an earlier
draft of this section — that statement is now checked against the
proof tiers as well as the design: §29.3 enumerates every tier
substitution this codebase forces, rather than declaring one and
implying the rest hold.

Every safety-relevant choice above is resolved with evidence from the
tree. Four items remain open, and all four are *engineering* choices
whose every outcome is safe — but item 1 carries three explicit
exclusions that are **not** open, because they bind a release gate:

1. **Default values — with three named exclusions.** §10's numbers
   are starting points; gate 6 requires re-deriving them from a
   measured benchmark run. For most of them, any value satisfying the
   fail-closed rules is safe and only the *documentation* obligation
   is binding.

   **`-gc-interval`, `-gc-min-advance-seqs` and
   `-gc-max-versions-per-pass` are excluded and are resolved now**
   (§10.3): together they cap `reclaim_rate`, and a triple below the
   workload's version-creation rate makes SL-19 — a required gate-2
   item — fail on a correct implementation. Gate 6 binds all three to
   the measured rate. They affect release acceptance, so they are not
   implementation-time choices.

   `-gc-max-keys-per-pass` is *not* excluded: it is a work bound
   carried in the command, so any value ≥ 1 is safe, deterministic
   and replica-identical.
2. **Histogram bucket boundaries.** §11.1's set is a proposal.
   Changing it changes no property.
3. **Whether `-wal-retain-extra-segments` earns its keep.** If SL-11
   and the real-process suite show `snapshot_serve_miss_total` is
   always zero at the default, the flag should be **dropped before
   release** rather than shipped as dead configuration. Dropping it is
   the preferred outcome; shipping an unexercised knob is not.
4. **Scrub scheduling.** `v0.6.0` ships scrub as an operator-triggered
   endpoint only. Whether a periodic scrub timer belongs here or in
   `enterprise-v1-plan.md` §11 (Operations) is a packaging question;
   this plan's position is §11, and shipping the endpoint alone is the
   conservative choice.

One item is a **risk to watch**, not a blocker: slice 7's
`mvcc.Store.Visible` signature change touches every read call site in
`internal/txn` and `internal/sql`. It is deliberately sequenced as its
own slice, with the watermark pinned at 0, so the mechanical change and
the behavioral change are never in the same commit. The `mergeScan`
conversion inside that slice (§15.2a) carries the higher risk of the
two, because nothing about it is compile-forced; SL-6b is the
backstop.

A second risk to watch: the ordered key index §14.4 requires moves
cost onto `ApplyCommit`'s first-write-of-a-key path. Gate 6 measures
it. If the measured write-path cost is unacceptable, the resolution
is a different index structure — never dropping `MaxKeys`, which is
the safety-relevant half.

## 36. Scope control — explicit non-goals

Restating `enterprise-v1-plan.md` §9/§10's own non-goals, plus this
document's additions surfaced during design. Each is V2 or later, and
none is authorized by this plan.

**Admission control**

- Per-credential, per-tenant, or per-client fair-share scheduling.
  ChronicleDB V1 has no tenant concept at all; admission is
  node-global.
- A general QoS/priority-class system for client traffic. Exactly the
  four lanes of §3.2 (K, A1, A2, B), no more.
- Predictive or adaptive admission control. Fixed,
  operator-configured thresholds only — no self-tuning controller, no
  latency-gradient/CoDel-style algorithm.
- Load shedding based on request *content* (key, table, statement
  shape).
- Cross-node coordination of admission decisions. Each node decides
  alone.
- Moving snapshot creation or backup export off the event loop (§4.4)
  — named, deferred, owned by a later release.

**Storage lifecycle**

- Compression of retained or archived data.
- Tiered or cold storage.
- Capacity-driven eviction of live data. V1 never deletes data a legal
  read could still need (C3).
- General-purpose defragmentation beyond whole-segment WAL compaction
  and GC.
- `RequestID` outcome-table retention/expiry (§28.2) — requires its
  own ADR because it directly touches `IDEMPOTENCY`. Out of scope for
  `v0.6.0`, but **not** an open-ended deferral: §24.4a records it as a
  `v1.0.0` blocker with a named owner gate
  (`enterprise-v1-plan.md` §17.1 item 3), because §17.1 item 3's
  "stable disk usage" wording cannot be satisfied while the table is
  unbounded. Either retention lands before `v1.0.0` or that wording is
  formally rescoped.
- Final-tombstone reclamation (§14.3).
- Standalone-mode GC (§14.6).
- Automatic scrub scheduling and automatic repair (§21.5).
- A manual "force GC now" endpoint (§25).
- Audit-log rotation (§28.3) — belongs to `enterprise-v1-plan.md` §11.
- Time-based WAL retention (§17.4).

**Unchanged from `v0.5.0` and earlier**

- No multi-shard, range directory, split/merge, replica placement,
  per-shard Raft, or distributed transactions
  ([`docs/enterprise-v1-plan.md`](enterprise-v1-plan.md) §18).
- No joint consensus, no automatic membership rebalancing.
- No maturity-level change: `v0.6.0` remains `EXTERNAL-REVIEW READY`.
  `ENTERPRISE-GRADE` is `v1.0.0`'s gate, and nothing here advances it.
